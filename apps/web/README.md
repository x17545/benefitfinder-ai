# 프론트엔드

작업 전에는 루트 지침과 이 경로의 [추가 에이전트 지침](AGENTS.md)을 함께 읽는다.

김하정이 UI 디자인·React 화면·백엔드 API 연결을 맡는다. 이현서는 요구사항·사용자 흐름·화면 구조·프로토타입을 설계하고, 양승현은 연결할 API·SSE를 제공한다. 상세 담당·인계는 [기능 명세 9장](../../docs/product/REQUIREMENTS.md#9-팀원별-담당-기능-및-협업-기준)을 따른다. 다른 영역 기여는 협업 규칙에 따라 조율한다.

화면·문구·동작의 원본은 [기획 명세 v2](../../docs/product/REQUIREMENTS.md)다. 선택지 13단계, 진행 상태, 조합·현재가치·상황 변화, 상세·빈 결과·오류, 기억하기·이미지 저장·이용 통계를 구현 대상으로 한다. [HTML 시안](../../docs/prototype/index.html)과 설계 이미지는 가상 데이터를 쓰는 화면 자료이며 제품 코드는 React로 작성한다.

## 확정 스택

- React + TypeScript strict + Vite를 사용하는 SPA로 확정했다.
- 패키지 관리자는 pnpm이다. 루트에서 pnpm 11.25.0을 pin하고 Node 24를 기준으로 한다. 웹 패키지 이름은 `@benefitfinder/web`이다. lockfile 생성과 의존성 설치는 루트에서 수행한다.
- 백엔드는 FastAPI + PostgreSQL로 확정했다. 프론트엔드는 DB에 직접 접근하지 않고 API 경유로만 데이터를 받는다.

## 실행 (저장소 루트 기준)

```sh
pnpm dev:web                                    # 웹 개발 서버 시작
pnpm --filter @benefitfinder/web dev            # 같은 서버를 패키지 지정으로 시작
pnpm --filter @benefitfinder/web lint           # ESLint
pnpm --filter @benefitfinder/web typecheck      # tsc -b
pnpm --filter @benefitfinder/web build          # tsc -b && vite build
pnpm --filter @benefitfinder/web preview        # 빌드 결과 미리보기
pnpm --filter @benefitfinder/web test           # vitest run
```

첫 설치는 루트에서 `pnpm install --frozen-lockfile`로 한다. 계약 타입은 이미 포함돼 있다. 계약 변경 후 `pnpm types:generate`를 실행하고 결과도 커밋한다. `pnpm check:web`로 전체 웹 검사를 실행한다. 설치·의존성 추가는 [시작 안내](../../docs/development/GETTING_STARTED.md)를 따른다.

## 실행 주소와 현재 화면

- 웹 개발 서버: `http://127.0.0.1:5173` (strictPort, 고정)
- 백엔드: `http://127.0.0.1:8000`, 생존 확인 `GET /health`
- 시작 화면에서 필수 동의 후 13단계 조건을 고르고 분석을 요청한다. 결과 화면은 서버가 준 조합·금액·기간별 현재가치 결과를 표시하며, 대안을 고르면 해당 조합의 포기한 정책과 근거를 연결한다. 선택한 기간에 결과가 없어도 다른 기간에 결과가 있으면 탭을 유지한다. 계산할 조합이 없어도 검수 대기·모집 종료·조건 미충족 목록과 계산 불가 안내는 유지하며, 6개 분기에 이들까지 모두 없을 때만 전체 빈 결과 화면을 표시한다.
- S4 상황 변화·S5 정책 상세 화면은 S3에서 진입한다. S4는 S3의 기간·현재가치 옵션을 전달하고 S5는 같은 정책·문서 버전의 진단과 설명을 표시한다. FastAPI에서 같은 가상 정책의 상황 변화 계산과 상세를 받아 표시한다. 가상 결과임을 안내하고 실제 신청 링크를 제공하지 않는다. 개발 서버에서만 404에 가상 예시를 표시하고 서버 오류·형식 불일치는 재시도 화면으로 구분한다. 배포 빌드에는 개발용 404 폴백이 없고 백엔드가 반환한 가상 정책은 예제라고 표시한다. 이용 안내(`/about`)·개인정보 처리방침(`/privacy`)은 현재 가상 추천 범위, 서버 무저장, 탭 임시 보관과 선택한 조건의 30일 기억하기, 전체 삭제를 안내한다. GA 통계는 미연결이다. 지역은 [공식 지역 API](../../backend/README.md#실제-지역-선택-api)를 사용하며 추천은 가상 MVP 정책을 계산한다. 실제 지역별 정책 조회·계산의 PostgreSQL 연결은 후속이다.
- 기억하기를 꺼도 입력·동의와 마지막 결과는 새로고침 복원을 위해 현재 탭에 남는다. 기억하기를 켜고 분석을 시작할 때만 조건을 localStorage에 추가 저장하고, 30일이 지난 뒤 다음 접속 때 삭제한다. 끄고 다시 분석하면 이전 localStorage 저장값을 지운다. 개인정보 페이지의 [지금 지우기]와 화면 하단 [내 정보 지우기]는 기억한 조건·현재 탭 입력·동의·결과를 함께 지운다. 안내 문구는 분석 직후 브라우저 자료까지 폐기한다고 표현하지 않는다.
- 지역 API 실패·빈 목록은 안내와 재시도를 표시하고 개발 모드도 가상 지역으로 대체하지 않는다. 시도 변경은 하위 선택을 초기화하고 하위가 하나면 자동 선택한다. 복원된 코드와 지난 조건 재사용은 현재 목록의 부모·자식 관계를 확인한다.
- 분석 화면 직접 진입·새로고침·재시도도 현재 지역 목록 확인 뒤에만 요청을 보낸다. 유효하지 않은 복원 코드는 지우고 지역 선택으로 돌아가며, 조회 중·오류·빈 목록일 때는 분석 POST를 보내지 않는다.
- 분석 실패 후 [예제 결과로 보기]는 개발 모드에만 제공한다. 가상 결과에는 개발용 표시를 붙인다. 운영 빌드에서는 API 오류를 그대로 표시하며 예제 진입 버튼을 제공하지 않는다.

## 연결

### 자료 상태와 서비스 메타데이터

공통 하단은 `GET /api/v1/meta`를 조회해 게시 자료의 갱신 시각(KST), 할인율 확인 상태, 조회 시점의 전체 이용자 공유 잔여 분석 횟수를 표시한다. 가상 모드에서는 가상 정책·자료 기준 시각임을 따로 표시하고, 시작·이용 안내도 같은 상태를 사용한다. 조회 전이나 실패 시에는 자료 유형·금리·횟수를 추정하지 않으며 실패 안내와 재시도를 제공한다. 이 조회는 분석 횟수를 차감하지 않는다.

화면 이동·창 포커스 복귀·추천 완료/실패와 상황 변화 요청 완료 후 다시 조회한다. 중복 요청은 이전 요청을 취소하고 늦게 도착한 결과는 버린다. 앱을 벗어나면 요청과 포커스 구독을 정리한다. 메타데이터는 메모리에만 두며 사용자 조건을 보내거나 저장하지 않는다. 이미 받은 추천의 금액·현재가치·순위를 이 값으로 다시 계산하지 않는다. 03시 실제 자동 갱신 완료 여부는 메타 응답만으로 보장하지 않는다.

### Vercel 배포 연결

Vercel의 프로젝트 Root Directory는 `apps/web`이며 `vercel.ts`가 `/api/*`·`/health`를 먼저 백엔드로 보내고 나머지 화면 주소는 `/index.html`로 연결한다. `/privacy`, `/about`, `/result` 직접 접근·새로고침도 SPA 라우터가 처리한다. [공식 프로그램 설정 안내](https://vercel.com/docs/project-configuration/vercel-ts)의 `config` export 형식을 사용하며 별도 런타임 의존성을 추가하지 않는다.

Preview에서 API를 쓰려면 **해당 구현을 포함한 백엔드의 HTTPS 원점**을 `API_PROXY_TARGET`으로 명시한다. 예: `https://branch-backend.example`. 이 값에 경로·인증정보·쿼리를 넣지 않는다. 값이 없거나 비어 있으면 웹은 빌드하고, `/api/*`와 `/health`는 `api/backend-unavailable.ts`의 HTTP 503·`dependency_unavailable` JSON으로 응답한다. 이 응답은 요청 본문을 읽거나 저장하지 않고 `Cache-Control: no-store`를 사용한다. 운영 API로 자동 연결하거나 정상 상태·가상 지역·추천 결과로 대체하지 않는다. 환경 이름을 알 수 없는 경우에도 같은 방식을 사용한다. 명시한 주소가 잘못됐으면 설정 오류로 빌드를 중단한다. Production은 같은 변수를 지정하거나 기존 `https://benefitfinder-ai.onrender.com`을 기본값으로 사용한다. `.env`의 Vite 개발 서버 설정은 배포 설정을 대신하지 않는다. `VITE_*`로 DB·모델 키를 전달하지 않는다.

백엔드는 저장소 루트의 [Render 설정](../../render.yaml)을 기준으로 준비한다. 이미 있는 서비스는 새로 만들기 전에 대상 서비스·연결 브랜치·환경을 확인한다. 이 파일은 자동 배포를 켜지 않으며, main 병합·배포·원격 설정 적용은 별도 승인 후 수행한다. 프론트·백엔드에 같은 구현을 반영한 뒤 `/health`의 JSON뿐 아니라 `/api/v1/options`의 지역 JSON, 가상 조건 추천·표시, `/privacy` 직접 접근을 모두 확인한다. `/health` 200만으로 정책 API 준비를 판단하지 않는다.

기본 추천은 가상 정책이며 `virtual_data: true`를 화면과 PNG에 표시한다. F13은 기본 안내로도 실행된다. AI 설명을 켜려면 백엔드와 같은 실행 환경에 Ollama/E4B를 따로 준비해야 하며, Render 환경 변수만으로 개발 PC의 모델을 호출할 수 없다.

### 개발 서버

- 개발 프록시는 `/api/v1`과 `/health`를 FastAPI로 넘긴다. 필요하면 `apps/web/.env.example`을 같은 폴더의 `.env`로 복사해 변경한다. 대상은 `API_PROXY_TARGET` (기본값 `http://127.0.0.1:8000`)이며 `VITE_` 접두사가 없으므로 브라우저에 공개되지 않는다.
- `/docs`와 `/openapi.json`은 프록시하지 않는다. API 문서는 `http://127.0.0.1:8000/docs`로 직접 연다.
- 운영은 same-origin 리버스 프록시를 권장하며 선택된 배포 주소를 사용한다.
- React 앱 자체는 정적 SPA 출력이며 서버가 아니다.
- 분석 POST는 SSE와 JSON 응답을 처리한다. `fetch` 스트림의 UTF-8 문자와 CRLF가 청크 사이에 나뉘어도 진행·최종 결과·오류를 해석하고 취소·60초 제한을 적용한다. 사용자 조건을 GET URL에 싣지 않는다.
- 추천 응답은 `1y`·`2y`·`all`만 받아들이며 6개 분기 안의 조합·정책·자격 판정·근거·부가 목록을 검증한 뒤 사용한다. 잘못된 응답은 분석 실패로 처리하고, 같은 검증에서 실패한 결과 캐시는 삭제한다.
- 정책 상세도 금액 설명·모집 정보·중복 제한·출처·근거의 중첩 구조를 검증한다. 실패한 상세는 화면 정보와 공유 캐시에 남기지 않고 기본 정책 이름으로 표시하며, 다음 화면 진입 때 다시 받는다.
- 입력 중인 값·동의·기억하기 선택은 sessionStorage `ypm.flow.v1`, 마지막 결과는 `ypm.lastResult`로 탭 안에서만 보관한다. 새로고침·뒤로 가기 때 복원하고 입력값이 실제로 바뀌면 이전 결과와 진행 요청을 무효화한다. 저장소가 차단되면 메모리로만 동작한다.
- 30일 기억하기는 선택한 경우 분석 시작 순간 localStorage `ypm.conditions.v1`에 저장한다. 시작 화면 재진입·새로고침 때 현재 탭의 선택을 유지하며, 지난 조건 카드가 있다는 이유만으로 기억하기를 켜지 않는다. [이 조건으로 다시 보기]는 저장된 조건을 재사용하고 기억하기를 켠다. [내 정보 지우기]는 저장값과 탭 안 입력·동의·결과를 모두 지운다. 민감한 조건 값은 GA에 보내지 않는다.

### 상황 변화 요청과 취소

상황 변화 요청은 효과가 유지된 다음에 전송을 시작한다. 개발 StrictMode의 setup-cleanup-setup이나 전송 전 화면 이동·빠른 상황 변경은 예약을 취소해 같은 진입으로 분석 횟수가 두 번 차감되지 않도록 한다. 전송 후 취소는 응답 반영을 막지만, 서버가 이미 예약한 분석 횟수를 되돌리는 동작은 아니다. `tests/simulationLifecycle.test.ts`에서 전송 전/후 취소와 늦은 응답·메타 갱신을 검사한다.

## 계약 타입

- 계약 요청·응답 타입은 수기로 중복 정의하지 않는다. `pnpm types:generate`로 `contracts/v1/*.schema.json`에서 파일별로 생성한다.
- health 타입은 `src/shared/api/generated/health.ts`에서 가져온다: `import type { HealthResponse } from './generated/health.js'`. `generated/` 폴더는 직접 수정하지 않는다.
- 화면에서 수집 원본이나 DB 구조를 직접 사용하지 않는다. `contracts/v1`을 기준으로 서버와 연결한다.
- 자격 판정과 수혜액 계산은 서버 결과를 그대로 표시한다. 같은 정책 규칙을 프론트엔드에서 다시 구현하지 않는다.
- 청년정책에만 필요한 입력과 문구는 `domains/youth`에 둔다. 공통 혜택 카드와 근거 표시는 재사용한다.
- 페이지별 파일은 관련 `features`에 두고, 실제 여러 기능에서 재사용할 때 `shared`로 이동한다.

## 개발 자료

- API가 준비되기 전에는 `contracts/fixtures`의 가상 요청과 응답으로 개발한다. 테스트와 개발 시에만 가상 데이터를 사용하고 기본 실행에서 가상 정책을 실제처럼 제공하지 않는다.
- 입력과 로딩과 빈 결과와 오류와 추가 확인 필요 상태를 함께 구현하고 키보드 접근과 입력 레이블을 확인한다.

### S5 신청 안내와 원문

현금·서비스 상세는 선택 필드 `application_guide`의 검수된 원문 인용으로 신청 방법·접수 기관·준비 서류를 표시한다. 인용 위치와 줄바꿈을 보존하고 HTML은 글자로 표시한다. 출처·문서 버전·확인일은 같은 정책의 하단 출처를 따른다. 운영 기관(`provider`)으로 접수 기관을 추정하지 않는다.

S3 조합·개별 목록과 S5 상세의 모집 태그와 신청 문구는 KST 날짜로 확인한다. 지난 종료일은 모집 끝남으로 표시하고, 신청 가능한 모집 중 상태에만 `신청하러 가기`를 표시한다. 모집 종료·예정·일정 미확인은 `공식 페이지 보기`로 구분한다. 마감 당일은 `D-0`, 마감까지 14일 이내만 D-n으로 표시한다. 저장된 `closed`를 날짜만으로 다시 열거나 `unknown`을 모집 중으로 바꾸지 않는다. 서버의 현금·서비스 추천과 상세도 같은 시작일·종료일 규칙을 적용하며, 검수된 시작일이 된 `upcoming`은 `open`으로 전환한다. 금액·자격·조합은 계속 서버의 분석 결과를 사용한다.

필드 생략/`null` 또는 `documents: null`이면 아직 확인하지 못했다는 안내를 표시하고, 사람이 확인한 빈 목록 `documents: []`일 때만 공식 자료에 서류 안내가 없다고 표시한다. 잘못된 중첩 인용·위치 누락·100개를 넘는 서류 목록은 API 클라이언트에서 거부한다. 가상 정책 안내와 실제 신청 버튼·마감 처리 규칙은 유지한다. 자세한 입력·검수 경계는 [게시 카탈로그](../../backend/src/benefitfinder/infrastructure/database/POLICY_CATALOG.md#신청-안내-f07)를 따른다.

### S6 서비스와 서비스형 상세

S3 → S6 → 서비스형 S5는 FastAPI와 공용 계약을 사용한다. S6는 서버의 목록·환산액·합계를 표시하고, S5는 공개 상세를 조회해 같은 버전의 추천 진단만 붙인다. 실제 수급액이 아닌 가상 서비스임을 표시하며 근거가 없는 항목은 환산하지 않는다.

백엔드가 서비스 필드를 생략하거나 목록이 비어 있으면 S3의 진입 링크를 숨긴다. 지난 분석에 마감된 서비스가 있으면 오래된 서비스 합계를 숨기고 재분석을 안내한다. 현금 결과는 유지한다. 배포·개발 모두 프론트가 임의로 서비스 예시를 채우지 않는다. 가상 사례 재현은 [F14 API 안내](../../backend/src/benefitfinder/api/README.md#f14-서비스-추천과-공개-상세)를 따른다.

## F13 결과 설명과 원문 근거

결과 화면의 정책 카드에 서버가 반환한 설명을 그대로 표시한다. 정책별 `ai_generated`가 true일 때만 AI 배지를 붙이며, false이면 ‘기본 안내’로 표시한다. 이전 응답에 정책별 플래그가 없으면 기존 최상위 플래그를 따른다. 모델 오류·시간 초과 시에도 서버의 기본 문구와 계산 금액·판정을 유지하고 클라이언트가 새 설명이나 근거를 만들지 않는다.

`원문 근거`를 펼치면 `ai_sources`의 원문 인용, 문서 위치, 버전, 확인일과 원문 링크를 볼 수 있다. 근거 목록이 없으면 펼침을 숨긴다. 키보드로 접고 펼칠 수 있는 native `details`를 사용하며, 펼침과 외부 링크는 정책 상세 링크 바깥에 둔다. 인용문은 HTML로 해석하지 않고 글자로 표시한다.

[API 실행 안내](../../backend/src/benefitfinder/api/README.md#f13-설명-실행)의 E4B 설정으로 백엔드를 실행한 뒤 `pnpm dev:web`으로 확인한다. 실제 API 결과를 연결하는 검증에서도 가상 정책·조건만 사용하며 원문·응답·화면 캡처는 Git 제외 로컬 경로에 둔다. 가상 검증은 실제 정책 사실·PostgreSQL 연결의 검증이 아니다.

```bash
pnpm --filter @benefitfinder/web test
```

### F12 승인 preview (not_yet_reviewed 선택 설명)

아직 조합 계산 전 목록에 메인이 주입한 preview가 있으면 ResultLists에서 실제 policy_name과 검증용 · 조합/자격/금액 확정 전·review_scope·기존 PolicyExplanation 재사용(AI/기본 안내·원문 quote·url·version·date)만 보여준다. 설명 없는 기존 항목은 기존 동작(짧은 이름·자격 진단 칩)을 유지하며, 생산 기본 추천 동작은 바꾸지 않는다. preview 설명 정책은 금액 null·원액 null·amount_status unknown·eligibility 빈 배열 구성이며, policy_id 동일·확정 금액 없음·자격 미확정(needs_review)은 isRecommendationResponse 런타임 검사로 보장하고 어기면 분석 실패로 처리한다. 수급·신청 보장 CTA는 추가하지 않는다.

`tests/policyExplanation.test.ts`는 생성 성공·기본 안내·부분 실패·이전 응답 호환, 인용·출처·확인일, HTML 이스케이프와 링크 중첩 방지를 검증한다. `tests/notYetReviewedPreview.test.ts`는 가상 데이터로 preview AI 출처·실패 fallback·범위 노출과 ID·확정 금액 불일치 거부를 검증한다.

13단계의 ‘내 조합 찾기’에서 실제 입력을 추천 요청으로 변환해 분석·결과 화면으로 이어진다. 개발 모드의 StrictMode가 분석 화면 effect를 즉시 정리하고 다시 실행하더라도 첫 시작 예약을 취소해 요청을 중복 전송하지 않는다. 이전 결과는 예약 전에 즉시 무효화하고, 화면을 떠나면 시작 예약과 진행 요청을 취소한다. `tests/loadingLifecycle.test.ts`에서 이 시작·취소 흐름을 검증한다.

이전 #16 단독 브랜치의 검증 기록: 시작 화면의 필수 동의 후 1~13단계를 실제로 선택하고, 12단계는 ‘건너뛰기’를 사용했다. 25세·가상 경기/수원·취업 준비·대학 졸업·미혼·혼자/무주택/세대주·월세/보증금 5천만 이하/월세 40~60만·소득 없음/재산 1억 2천만 이하·특수 조건 없음·취업과 주거 관심·과거 수혜 없음 조건을 사용했다. 당시 지역 API 미구현으로 개발용 가상 목록을 사용했다. 현재 통합 코드는 공식 지역 API를 쓰며, 이전 기록을 실제 지역·정책 사실 검증으로 해석하지 않는다. E4B 성공·모델 오류·시간 초과마다 이 입력을 다시 진행해 분석당 서버 도착 요청 1회와 설명·기본 안내의 결과 표시를 확인했다.

## 실행과 검증

- `lint`는 ESLint flat config (TS/React hooks)로 실행한다. `eslint-disable`이나 `any` 우회로 오류를 숨기지 않는다.
- `typecheck`와 `build`는 `tsc -b`를 사용한다.
- `test`는 `vitest run`이며 추천·정책 상세의 중첩 응답과 기간 키·SSE 청크 경계, 요청 변환, 입력/결과 복원·무효화·삭제, 기억하기 선택 유지, 기간별 빈 결과·계산 불가·보완 목록, 선택 조합의 제외 목록과 상세 재시도를 검증한다.
- 기능과 회귀 테스트는 필요해졌을 때 추가한다. 문서 변경에는 더미 테스트를 쓰지 않는다.

상세 설계는 [아키텍처 문서](../../docs/architecture/ARCHITECTURE.md)를 참고한다.

추가 회의에 따라 초기 MVP의 관심 선택·결과·상세는 취업·주거 두 분류만 노출한다. 설계 PNG는 이전 범위를 포함한 화면 이력이며 현재 문구와 가상 금액은 [현행 기능 명세](../../docs/product/REQUIREMENTS.md)를 따른다. 클릭 시안도 참고 자료이며 명세와 다르면 명세를 기준으로 맞춘다.
