# 기획 개요·일정·제출물

이 문서는 제품의 배경과 목표, 일정, 평가 준비를 다룬다. 문서 정리 전 기획서의 고유 내용은 유지하고 기능·계산·기술·역할·Git 규칙의 중복 설명은 해당 기준 문서로 연결했다. 이전 전체 본문과 변경 이력은 [기획서 v2.5 기록](../archive/PROJECT_PLAN_v2.5_ARCHIVE.md)에 보존한다.

## 1. 제품과 목표

프로젝트 이름은 **AI 혜택 코치 (BenefitFinder AI)**, 화면 이름은 **청년 정책 매니저**다. 코디세이 Final Project의 5인 팀 프로젝트이며 제출 마감일은 **2026-11-25**다.

사용자가 13단계 선택 입력으로 조건을 고르면, 정책별 자격과 중복 수급 제한을 반영해 **함께 받을 수 있는 지원금 조합을 총액순으로 비교**한다. 추천 조합과 대안, 포기하는 지원금·현재가치·상황 변화에 따른 차이를 확인하고 신청 준비까지 이어지는 서비스를 목표로 한다.

초기 MVP는 만 19~39세 청년의 취업·주거 혜택이다. 생활·자산형성·교육·장학 등 나머지 청년 분야와 다른 대상의 혜택은 확장 단계에서 추가한다. 나이가 대상 범위를 벗어나면 혜택이 적을 수 있음을 안내하며 이용을 막지 않는다. 기업·소상공인 정책은 초기 대상이 아니다.

주요 사용자는 취업준비생, 대학생, 사회초년생이다. 선택 입력으로 정책 검색 조건을 만들고, 조건별 충족·미충족·확인 필요와 공식 근거를 이해하도록 돕는다. 분석은 최종 수급 자격을 확정하지 않으며 공식 기관 안내로 연결한다.

기능·화면·문구·계산 규칙·완료 조건의 기준은 [기능 명세](REQUIREMENTS.md)다. 문장 입력·챗봇 대신 선택 입력을 사용한다. 데이터 준비의 Agent와 사용자 요청의 판정·계산은 [정책 데이터 준비](../architecture/POLICY_DATA_PIPELINE.md)에 따라 구분한다.

## 2. 추진 배경과 문제 정의

아래는 2026-10-23 작성된 ‘놓친 혜택 찾기’ 제안서(v1)에서 제기한 사용자 문제를 현행 v2의 취업·주거 범위로 구체화한 것이다. 사용자 인터뷰나 경쟁 서비스 전체에 대한 조사 결과로 확정한 사실은 아니며, 실제 사용자 테스트에서 검증할 문제 가설이다. 기능·화면·계산·수락 조건은 현행 명세를 유지한다.

### 2.1 누가, 언제 어려움을 겪는가

주요 대상은 취업을 준비하거나 첫 직장을 다니며 주거비를 줄이려는 청년이다. 지원금을 알아보는 시점뿐 아니라 취업·독립·소득 변화로 현재 받을 수 있는 혜택이 달라지는 시점에도 비교가 필요하다.

사용자는 여러 공고를 찾은 뒤 자신의 조건에 맞는지, 함께 받을 수 있는지, 어떤 선택의 총액이 큰지까지 판단해야 한다. 기획이 집중하는 지점은 **혜택을 발견한 뒤에도 남아 있는 선택과 계산의 부담**이다.

### 2.2 문제의 원인과 사용자 부담

| 원인 | 사용자가 직접 해야 하는 일 | 놓칠 수 있는 판단 |
|---|---|---|
| 정책과 안내가 여러 기관·문서에 나뉨 | 관련 공고와 신청 정보를 모으기 | 받을 수 있는 정책이나 신청 준비사항 누락 |
| 나이·소득·지역·가구 조건이 정책마다 다름 | 공고의 조건을 내 상황과 대조하기 | 미확인 조건을 충족으로 오해 |
| 중복 수급 제한에 기간·예외·이력 조건이 얽힘 | 여러 정책의 원문을 함께 읽고 관계 확인하기 | 개별 자격을 충족하면 모두 함께 받을 수 있다고 오해 |
| 지급 기간·시점·형태가 다름 | 같은 기간의 총액과 현재가치로 비교하기 | 단일 금액이 큰 정책을 선택하다 더 유리한 조합 누락 |
| 취업·독립·소득 변화로 적용 조건이 달라짐 | 변경 후의 자격·조합·지원액을 다시 계산하기 | 끊기는 혜택이나 새로 받을 수 있는 혜택 누락 |

그 결과 비교에 시간과 수고가 들고, 함께 받을 수 없는 지원금을 합산하거나 받을 수 있는 조합을 놓칠 수 있다. 지원금 하나의 수급 가능성만 확인해서는 조합의 총액과 선택 이유까지 알기 어렵다.

### 2.3 핵심 문제 정의

**청년은 자신의 조건에 맞아 보이는 정책을 찾은 뒤에도, 중복 수급 제한을 만족하는 조합 중 무엇이 가장 이득이고 상황이 바뀌면 그 결과가 어떻게 달라지는지 스스로 판단해야 한다.**

따라서 추천의 단위는 함께 받을 수 있는 지원금의 조합이다. 개별 금액이 큰 정책을 먼저 고르면 더 큰 총액의 조합을 놓칠 수 있다. [README의 가상 예시](../../README.md#왜-조합을-비교해야-할까)는 이 선택 문제를 설명하며, 실제 정책이나 명세 8.3의 정답 자료를 추가·변경하지 않는다.

### 2.4 해결 방향과 사용자가 얻는 결과

1. **내 조건으로 비교를 시작한다.** 13단계 선택 입력으로 나이·소득·주거 등의 조건을 구조화하고, 충족·미충족·확인 필요와 근거를 보여 준다.
2. **함께 받을 수 있는 조합과 선택의 대가를 본다.** 검수된 중복 제한을 적용해 조합별 총액을 비교하고, 대안·포기하는 지원금·기간·현재가치를 함께 보여 준다.
3. **상황이 바뀐 뒤도 비교한다.** 취업·독립·소득 변화 시 끊기거나 새로 받을 수 있는 정책과 총액 변화를 확인한다. 소득 변화의 지원금 영향과 혜택 절벽은 명세 F06의 계산 기준을 따른다.
4. **확인과 신청으로 이어진다.** 추천 이유·미확인 조건·공식 원문·신청 방법·준비사항을 연결한다.

원문에 분산된 중복 제한·예외는 데이터 Agent가 규칙 후보로 추출하고 사람이 검수한 뒤 게시한다. 사용자 요청에서는 게시된 데이터와 코드로 판정·계산한다. 미확인 중복 조건을 동시 수급 허용으로 추정하지 않으며, 확인 필요 조합은 확정 수급을 보장하지 않는다. 분석은 최종 신청 자격을 확정하지 않는다.

세부 처리와 수락 조건은 [기능 명세 5장](REQUIREMENTS.md#5-기능-상세-요구사항)을 따른다. v1은 문제 배경을 참고하는 자료이며, 선택 입력·취업/주거 범위·사용자 요청의 코드 계산 등 현행 v2 결정을 기준으로 구현한다.

### 2.5 사용자 테스트에서 확인할 것

- 사용자가 자신의 조건을 공고와 대조하고 중복 제한·조합 총액을 비교할 때 실제로 어디서 막히는가?
- 추천 조합과 대안, 포기하는 지원금과 근거를 보고 선택 이유를 설명할 수 있는가?
- 상황 변화 화면에서 지원금·총액이 달라지는 이유와 확인할 조건을 이해하는가?
- 결과에서 공식 공고와 신청 안내까지 이어갈 수 있는가?

검증은 [사용자 테스트 진행안](USER_TEST.md)과 기능 명세 8장의 기존 성공 기준을 따른다. 새 성과 수치나 경쟁 서비스에 대한 단정은 추가하지 않는다.

## 3. 성공 기준과 평가

### 성공 기준

- 13단계 선택 입력으로 조건을 수집할 수 있다.
- 실제 정책 데이터를 검색하여 조합을 계산할 수 있다.
- 정책별 자격 조건과 판단 근거를 표시할 수 있다.
- 정보가 부족할 때 추가 확인이 필요함을 안내한다.
- 추천 조합의 공식 출처를 확인할 수 있다.
- 외부에서 서비스에 접속하고 핵심 기능을 이용할 수 있다.
- 사용자 5명 이상의 테스트와 피드백 기록을 확보한다.
- 팀원 5명의 실질적인 개발과 문서 기여를 기록한다.

### 평가 준비와 완료 기준

- F01~F11의 수락 조건과 공식 정책의 검수 상태를 확인한다. F02 검색·F03 분석 흐름도 실제로 동작해야 한다.
- 자격 진단의 조건별 근거·확인 필요와 조합 비교의 수치를 검증한다. 설명이 판정 근거 템플릿임을 명확히 한다.
- 외부에서 접근할 수 있는 배포 URL과 평가자가 따라 할 테스트 방법을 제공한다. 현재 배포 완료를 뜻하지 않는다.
- 사용자 5명 이상을 테스트하고 피드백·개선 내용을 남긴다. 실제 조건 값은 관찰 기록에 남기지 않는다.
- GitHub Issue·PR로 팀원 5명의 기여와 주요 결정을 기록한다.
- 최종 제출물과 개인정보 처리, 배포 서비스의 전체 흐름을 확인한다.

세부 기능·정답·성공 수치는 [기능 명세 8장](REQUIREMENTS.md#8-테스트), 진행 방법과 기록표는 [사용자 테스트](USER_TEST.md)를 따른다.

### API 승인 지연 시 개발

API 승인이 지연되면 공식 정책 페이지에서 사람이 확인한 자료로 검색·진단 기능을 개발한다. 이는 개발 중 대안이며, 운영 수집 범위는 기능 명세의 두 정책 API 기준을 유지한다. 실제 수집 자료는 Git 제외 경로에 두고 공유 예제는 가상값을 쓴다. 정책 형식 차이·원문 변경·판정 오류의 대응은 [정책 데이터 준비](../architecture/POLICY_DATA_PIPELINE.md)의 검수·확인 필요·버전 관리 기준을 따른다.
