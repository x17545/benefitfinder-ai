# 기획 개요·일정·제출물

이 문서는 제품의 배경과 목표, 일정, 평가 준비를 다룬다. 문서 정리 전 기획서의 고유 내용은 유지하고 기능·계산·기술·역할·Git 규칙의 중복 설명은 해당 기준 문서로 연결했다. 이전 전체 본문과 변경 이력은 [기획서 v2.5 기록](../archive/PROJECT_PLAN_v2.5_ARCHIVE.md)에 보존한다.

## 1. 제품과 목표

프로젝트 이름은 **AI 혜택 코치 (BenefitFinder AI)**, 화면 이름은 **청년 정책 매니저**다. 코디세이 Final Project의 5인 팀 프로젝트이며 제출 마감일은 **2026-11-25**다.

사용자가 13단계 선택 입력으로 조건을 고르면, 정책별 자격과 중복 수급 제한을 반영해 **함께 받을 수 있는 지원금 조합을 총액순으로 비교**한다. 추천 조합과 대안, 포기하는 지원금·현재가치·상황 변화에 따른 차이를 확인하고 신청 준비까지 이어지는 서비스를 목표로 한다.

초기 MVP는 만 19~39세 청년의 취업·주거 혜택이다. 생활·자산형성·교육·장학 등 나머지 청년 분야와 다른 대상의 혜택은 확장 단계에서 추가한다. 나이가 대상 범위를 벗어나면 혜택이 적을 수 있음을 안내하며 이용을 막지 않는다. 기업·소상공인 정책은 초기 대상이 아니다.

주요 사용자는 취업준비생, 대학생, 사회초년생이다. 선택 입력으로 정책 검색 조건을 만들고, 조건별 충족·미충족·확인 필요와 공식 근거를 이해하도록 돕는다. 분석은 최종 수급 자격을 확정하지 않으며 공식 기관 안내로 연결한다.

기능·화면·문구·계산 규칙·완료 조건의 기준은 [기능 명세](REQUIREMENTS.md)다. 문장 입력·챗봇 대신 선택 입력을 사용한다. 데이터 준비의 Agent와 사용자 요청의 판정·계산은 [정책 데이터 준비](../architecture/POLICY_DATA_PIPELINE.md)에 따라 구분한다.

## 2. 추진 배경과 문제 정의

아래는 기획에서 정의한 문제와 지향점이다. 기존 서비스 전체에 대한 조사·검증 결과를 뜻하지 않는다.

### 2.1 추진 배경

정부와 지방자치단체에서는 청년을 대상으로 주거, 취업, 생활안정 등 다양한 지원정책을 운영하고 있다. 정책이 여러 기관과 웹사이트에 분산되어 있고 정책마다 신청 대상과 자격 조건이 달라, 사용자가 자신에게 맞는 정책을 찾기 어렵다.

청년들은 본인 생활 상황을 정책 검색 조건으로 바꾸거나 복잡한 자격요건을 해석하는 과정에서 어려움을 겪는다. 이에 정책 원문을 분석·정제해 조건과 근거를 구조화하고, 공식 정책정보를 바탕으로 맞춤형 혜택 조합을 계산하는 서비스를 만든다.

### 2.2 기존 서비스의 한계

기존 청년정책 플랫폼에서도 정책 검색, 조건별 조회, AI 상담, 자격 진단 등을 제공한다. 그러나 어떤 정책이 있는지를 알려 주는 데 그치고, 어떤 지원금 조합을 받는 것이 가장 이득인지를 계산해 주지는 않는다.

본 프로젝트는 정책 목록 제공을 넘어, 중복 수혜 제한을 반영한 조합 계산과 총액 비교, 상황 변화 시뮬레이션까지 하나의 사용자 경험으로 연결한다.

### 2.3 해결하고자 하는 문제

1. 사용자가 자신에게 필요한 정책을 찾기 어렵다.
2. 정책별 자격 조건이 복잡하여 이해하기 어렵다.
3. 여러 정책 중 무엇을 우선 확인할지 판단하기 어렵다.
4. 정책이 추천된 이유와 부족한 조건을 파악하기 어렵다.
5. 신청 전 확인사항과 준비서류를 찾는 과정이 번거롭다.
6. 함께 받을 수 있는 조합과 총액을 비교하기 어렵다.

### 2.4 제안하는 해결 방법

1. 13단계 선택 입력으로 사용자 조건을 구조화한다.
2. 공식 청년정책 데이터에서 관련 정책을 검색한다.
3. 사용자 조건과 정책별 자격요건을 비교한다.
4. 조건별 충족, 미충족, 확인 필요를 표시한다.
5. 중복 수혜 제한을 반영해 총액이 가장 큰 조합을 계산한다.
6. 포기하는 지원금과 현재가치, 실효한계세율을 함께 보여 준다.
7. 추천 근거와 추가 확인사항, 신청 준비사항을 안내한다.

분석 결과는 참고용이며 최종 신청 자격을 확정하지 않는다.

### 2.5 기존 서비스와의 차별점

- 선택 입력과 단계별 정책정보 조회 결합
- 구조화 DB 조건 기반 공식 정책정보 근거 인용
- 조건별 근거를 제시하는 자격 진단
- 중복 제한 반영 최적 조합 계산과 총액 비교
- 상황 변화 시뮬레이션과 실효한계세율 안내
- 추천부터 신청 준비까지 연결되는 통합 경험

## 3. 성공 기준과 평가

### 성공 기준

- 13단계 선택 입력으로 조건을 수집할 수 있다.
- 실제 정책 데이터를 검색하여 조합을 계산할 수 있다.
- 정책별 자격 조건과 판단 근거를 표시할 수 있다.
- 정보가 부족할 때 추가 확인이 필요함을 안내한다.
- 추천 조합의 공식 출처를 확인할 수 있다.
- 외부에서 서비스에 접속하고 핵심 기능을 이용할 수 있다.
- 사용자 5명 이상의 테스트와 피드백 기록을 확보한다.
- 팀원 5명의 실질적인 개발과 문서 기여를 기록한다.

### 평가 준비와 완료 기준

- F01~F11의 수락 조건과 공식 정책의 검수 상태를 확인한다. F02 검색·F03 분석 흐름도 실제로 동작해야 한다.
- 자격 진단의 조건별 근거·확인 필요와 조합 비교의 수치를 검증한다. 설명이 판정 근거 템플릿임을 명확히 한다.
- 외부에서 접근할 수 있는 배포 URL과 평가자가 따라 할 테스트 방법을 제공한다. 현재 배포 완료를 뜻하지 않는다.
- 사용자 5명 이상을 테스트하고 피드백·개선 내용을 남긴다. 실제 조건 값은 관찰 기록에 남기지 않는다.
- GitHub Issue·PR로 팀원 5명의 기여와 주요 결정을 기록한다.
- 최종 제출물과 개인정보 처리, 배포 서비스의 전체 흐름을 확인한다.

세부 기능·정답·성공 수치는 [기능 명세 8장](REQUIREMENTS.md#8-테스트), 진행 방법과 기록표는 [사용자 테스트](USER_TEST.md)를 따른다.

프로젝트 제출 마감일은 2026년 11월 25일이다.

| 기간 | 주요 목표 |
|---|---|
| 10/24부터 10/26 | 기획서 초안, 팀 역할 분담, GitHub 협업 준비 |
| 10/27부터 11/02 | 요구사항 검토, 공통 코드 구조 확인, 데이터와 API 설계 |
| 11/03부터 11/09 | 조건 선택 입력, 정책 검색(구조화 DB 조건), 분석 흐름 핵심 기능 개발 |
| 11/10부터 11/13 | 자격 진단, 최적 조합, 신청 안내와 화면 통합 |
| 11/14부터 11/19 | 1차 배포, 통합 테스트, 실제 사용자 5명 이상 테스트 |
| 11/20부터 11/23 | 오류 수정, 사용자 피드백 반영, 문서와 발표 자료 완성 |
| 11/24 | 최종 제출물과 배포 서비스 점검 |
| 11/25 | 최종 제출 |

상세 작업 일정은 GitHub Issue로 관리한다. 일정이 지연되면 범위를 어떻게 조정할지는 팀 회의에서 정한다.

### API 승인 지연 시 개발

API 승인이 지연되면 공식 정책 페이지에서 사람이 확인한 자료로 검색·진단 기능을 개발한다. 이는 개발 중 대안이며, 운영 수집 범위는 기능 명세의 두 정책 API 기준을 유지한다. 실제 수집 자료는 Git 제외 경로에 두고 공유 예제는 가상값을 쓴다. 정책 형식 차이·원문 변경·판정 오류의 대응은 [정책 데이터 준비](../architecture/POLICY_DATA_PIPELINE.md)의 검수·확인 필요·버전 관리 기준을 따른다.
