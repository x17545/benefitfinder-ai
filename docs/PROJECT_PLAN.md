## 1. 프로젝트 개요

### 1.1 프로젝트명

AI 혜택 코치 (BenefitFinder AI)

### 1.2 프로젝트 소개

AI 혜택 코치(BenefitFinder AI)는 사용자가 자신의 상황과
고민을 자연어로 입력하면, AI가 사용자 조건을 분석하고
공식 청년 지원정책을 검색하여 맞춤형 혜택을 추천하는
AI 기반 청년정책 안내 서비스이다.

본 프로젝트는 B안 단계적 포트폴리오형 개발 방향을
기준으로 검토한다.

초기 버전에서는 사용자에게 적합한 청년정책을
최대 5개까지 함께 제시하고, 정책별 자격 진단 결과,
추천 이유 및 신청 준비사항을 안내한다.

단, 여러 정책을 함께 추천하는 것은
동시 수급 가능성을 보장하는 의미가 아니다.

공식 근거에 기반한 중복 수혜 가능성 분석은
핵심 기능 완성 후 추가 구현을 검토한다.



### 1.3 핵심 서비스 흐름

1. 자연어로 사용자 상황 입력
2. AI를 통한 사용자 조건 자동 추출
3. 사용자 조건 확인 및 수정
4. 정책에 필요한 가구·부모님 정보 선택 입력
5. 공식 청년정책 데이터 및 근거 검색
6. 규칙 기반 정책별 자격 진단
7. 맞춤형 혜택 포트폴리오 추천 (최대 5개)
8. 정책 상세정보 및 신청 준비사항 안내

※ 부모님 소득·재산 정보는 정책상 필요한 경우에만
선택적으로 요청하며, 입력하지 않아도 기본 검색을
진행할 수 있도록 설계한다.

※ 추가 정보가 없어 자격을 판단하기 어려우면
'추가 확인 필요'로 표시한다.


### 1.4 핵심 기술
- RAG: 공식 청년정책 데이터 기반 검색 및 답변
- AI Agent: 필요한 검색 및 상세조회 도구 선택
- 규칙 기반 진단: 명확한 자격 조건 비교
- 생성형 AI: 조건 해석 및 추천 이유 설명

### 1.5 프로젝트 목표
1. 자연어를 통해 청년 지원정책을 쉽게 검색한다.
2. 사용자 조건과 정책 자격요건을 비교한다.
3. 추천 이유와 추가 확인사항을 명확하게 안내한다.
4. 실제 정책정보를 근거로 신뢰할 수 있는 답변을 제공한다.
5. 외부에서 사용할 수 있는 웹서비스를 완성한다.
6. 관련 청년정책을 포트폴리오 형태로 함께 제시하여
   사용자가 여러 혜택을 한눈에 비교할 수 있도록 한다.

※ AI 진단은 최종 수급 자격을 확정하지 않는다.
※ 최종 자격과 신청 조건은 공식 기관 안내를 확인해야 한다.

## 2. 추진 배경 및 문제 정의

### 2.1 추진 배경

정부 및 지방자치단체에서는 청년을 대상으로 주거,
취업, 생활안정 등 다양한 지원정책을 운영하고 있다.

하지만 이러한 정책은 여러 기관과 웹사이트에
분산되어 있으며, 정책마다 신청 대상과 자격 조건이
달라 사용자가 자신에게 적합한 정책을 찾기 어렵다.

특히 청년들은 본인의 생활 상황을 정책 검색 조건으로
변환하거나 복잡한 자격요건을 해석하는 과정에서
어려움을 겪을 수 있다.

이에 본 프로젝트에서는 생성형 AI를 활용하여
사용자의 자연어 상황을 이해하고, 공식 정책정보를
기반으로 맞춤형 혜택을 안내하는 서비스를 개발한다.

### 2.2 기존 서비스의 한계

기존 청년정책 플랫폼에서도 정책 검색, 조건별 조회,
AI 상담, 자격 진단 등의 기능을 제공하고 있다.

그러나 서비스별로 제공 기능과 이용 방식이 다르며,
사용자가 자신의 상황을 입력한 후 정책 검색,
조건별 비교, 추천 이유 확인, 신청 준비 안내까지
일관된 흐름으로 이용하는 데에는 개선 여지가 있다.

본 프로젝트는 기존 서비스에 없는 기능을
단순히 추가하기보다 이러한 과정을 하나의
사용자 경험으로 통합하는 데 초점을 맞춘다.

### 2.3 해결하고자 하는 문제

1. 사용자가 자신에게 필요한 정책을 찾기 어렵다.
2. 정책별 자격 조건이 복잡하여 이해하기 어렵다.
3. 여러 정책 중 무엇을 우선 확인할지 판단하기 어렵다.
4. 정책이 추천된 이유와 부족한 조건을 파악하기 어렵다.
5. 신청 전 확인사항과 준비서류를 찾는 과정이 번거롭다.

### 2.4 제안하는 해결 방법

AI 혜택 코치는 다음과 같은 방식으로 문제를 해결한다.

1. 자연어 입력을 통해 사용자 상황을 분석한다.
2. 공식 청년정책 데이터에서 관련 정책을 검색한다.
3. 사용자 조건과 정책별 자격요건을 비교한다.
4. 조건별 충족, 미충족, 추가 확인 필요를 표시한다.
5. 관련성과 신청기간 등을 고려해 추천 우선순위를 정한다.
6. 추천 근거, 추가 확인사항, 신청 준비사항을 안내한다.

단, AI의 분석 결과는 참고용이며
최종 신청 자격을 확정하지 않는다.

### 2.5 기존 서비스와의 차별점

본 서비스의 차별점은 다음과 같다.

- 자연어를 통한 복합적인 사용자 상황 이해
- AI Agent를 활용한 단계별 정책정보 조회
- RAG를 활용한 공식 정책정보 기반 답변
- 조건별 근거를 제시하는 자격 진단 카드
- 사용자 상황에 맞는 추가 확인사항 안내
- 추천부터 신청 준비까지 연결되는 통합 경험

## 3. 프로젝트 목표

### 3.1 핵심 목표

본 프로젝트의 핵심 목표는 사용자가 자연어로 자신의
상황을 설명하면 AI가 관련 청년정책을 검색하고,
자격요건을 분석하여 신청 준비까지 안내하는
웹서비스를 구현하는 것이다.

단순한 정책 검색을 넘어 사용자의 상황과 정책 조건을
연결하고, 추천 결과의 근거를 이해할 수 있도록 한다.

### 3.2 세부 목표

1. 자연어 기반 사용자 상황 분석
   - 나이, 거주지역, 취업 상태, 관심 분야 등을 추출한다.
   - 입력되지 않은 정보는 임의로 추정하지 않는다.

2. 공식 정책정보 기반 검색
   - 정부 및 공공기관의 정책 데이터를 활용한다.
   - RAG를 통해 관련 정책의 근거를 검색한다.

3. 조건별 자격 진단
   - 정책 조건과 사용자 정보를 비교한다.
   - 충족, 미충족, 추가 확인 필요로 구분한다.
   - 판단 근거를 함께 제공한다.

4. 맞춤형 정책 추천
   - 사용자의 관심사와 정책 적합성을 고려한다.
   - 추천 이유와 우선 확인할 정책을 제시한다.

5. 신청 준비 안내
   - 신청기간, 신청 방법, 준비사항을 안내한다.
   - 공식 신청 페이지 또는 정책 원문을 연결한다.

6. 실제 사용 가능한 서비스 완성
   - 외부 접속 가능한 웹서비스로 배포한다.
   - 최소 5명의 실제 사용자 테스트를 진행한다.
   - 사용자 피드백을 반영하여 개선한다.

### 3.3 프로젝트 성공 기준

- 자연어 입력에서 주요 사용자 조건을 추출할 수 있다.
- 실제 정책 데이터를 검색하여 추천할 수 있다.
- 정책별 자격 조건과 판단 근거를 표시할 수 있다.
- 정보가 부족할 때 추가 확인이 필요함을 안내한다.
- 추천 정책의 공식 출처를 확인할 수 있다.
- 외부에서 서비스에 접속하고 핵심 기능을 이용할 수 있다.
- 사용자 5명 이상의 테스트 및 피드백 기록을 확보한다.
- 팀원 5명의 실질적인 개발 및 문서 기여를 기록한다.

## 4. 타깃 사용자

### 4.1 주요 타깃

본 서비스의 초기 타깃은 만 19~34세 청년이다.

이 연령 범위는 초기 서비스의 개발 및 테스트 범위이며,
실제 지원정책의 연령 기준은 개별 정책 공고를 따른다.

### 4.2 세부 사용자 유형

#### 유형 A. 취업준비생

- 취업을 준비하고 있는 청년
- 구직활동비 및 생활비 지원에 관심이 있는 사용자
- 자신에게 적합한 취업 지원정책을 찾고 싶은 사용자

#### 유형 B. 대학생

- 대학에 재학 중인 청년
- 주거비 및 생활비 부담이 있는 사용자
- 학업과 취업 준비에 필요한 지원을 찾는 사용자

#### 유형 C. 사회초년생

- 취업 후 경제적으로 독립하기 시작한 청년
- 월세 및 생활비 부담이 있는 사용자
- 주거 지원 및 자산형성 정책에 관심이 있는 사용자

### 4.3 초기 지원 지역

- 전국 공통 청년 지원정책
- 경상남도 청년 지원정책
- 창원시 청년 지원정책

다른 지방자치단체의 개별 정책은 초기 서비스의
지원 범위에서 제외한다.

단, 전국 공통 정책은 해당 정책의 실제 지역 조건에
따라 추천하며, 지역별 지원 범위의 한계를 명시한다.

### 4.4 대표 사용자 시나리오

사용자 입력 예시:

"나는 25살이고 창원에서 자취 중인 취준생이야.
월세가 부담돼."

AI가 추출하는 정보:

- 나이: 25세
- 거주지역: 경상남도 창원시
- 취업 상태: 취업준비생
- 주거 상황: 자취
- 관심 분야: 주거비 지원
- 소득 정보: 미입력
- 가구 정보: 미입력

서비스 처리 과정:

1. 자연어에서 사용자 상황을 추출한다.
2. 주거 관련 청년 지원정책을 검색한다.
3. 정책별 연령, 지역, 소득 등 자격 조건을 비교한다.
4. 확인 가능한 조건과 추가 확인이 필요한 조건을 구분한다.
5. 관련성이 높은 정책을 우선 추천한다.
6. 추천 이유와 신청 준비사항을 안내한다.

7. 관련 정책이 여러 개라면 최대 5개까지 함께 추천한다.
8. 정책상 부모님 또는 원가구 정보가 필요한 경우
   사용자가 해당 정보를 선택적으로 입력할 수 있다.
9. 추가 정보를 모르는 경우 자격을 임의로 확정하지 않고
   '추가 확인 필요'로 표시한다.

※ 여러 정책의 동시 추천은 중복 수혜 가능성을
보장하는 의미가 아니다.

소득이나 가구 정보처럼 입력되지 않은 항목은
임의로 판단하지 않고 추가 확인 필요로 표시한다.

### 4.5 사용자 기대 효과

- 정책을 찾는 데 필요한 검색 부담 감소
- 복잡한 자격 조건에 대한 이해 향상
- 자신의 상황에 맞는 정책을 우선 확인 가능
- 신청 전 확인사항과 준비 과정 파악

## 5. 핵심 서비스 및 사용자 시나리오

### 5.1 핵심 서비스 개념

AI 혜택 코치는 사용자의 자연어 입력을 바탕으로
관련 청년정책을 검색하고 자격 조건을 비교하여
맞춤형 정책과 신청 준비사항을 안내하는 서비스이다.

핵심 서비스는 다음 7단계로 구성한다.

1. 자연어 상황 입력
2. 사용자 조건 자동 추출 및 수정
3. 정책에 필요한 가구·부모님 정보 선택 입력
4. 공식 청년정책 및 근거 검색
5. 정책별 자격 조건 진단
6. 맞춤형 혜택 포트폴리오 추천 (최대 5개)
7. 정책 상세정보 및 신청 준비사항 안내

부모님 소득·재산 정보는 관련 정책에서 요구할 경우에만
선택적으로 확인하며, 정보가 부족하면
'추가 확인 필요'로 안내한다.

초기 혜택 포트폴리오는 관련 정책을 함께 보여주는
기능이며, 동시 수급 가능성을 확정하지 않는다.

### 5.2 사용자 이용 흐름

#### STEP 1. 자연어 상황 입력

사용자는 검색 조건을 일일이 선택하지 않고
자신의 상황과 고민을 자유롭게 입력한다.

예시:
"나는 25살이고 창원에서 자취 중인 취준생이야.
월세가 부담돼."

#### STEP 2. 사용자 조건 자동 추출

생성형 AI가 입력 문장에서 주요 정보를 추출한다.

- 나이: 25세
- 지역: 창원시
- 취업 상태: 취업준비생
- 주거 상황: 자취
- 관심 분야: 주거비
- 소득: 미입력

추출한 조건은 사용자가 확인하거나 수정할 수 있다.


정책상 필요한 경우 부모님과의 거주 여부,
가구 구성, 부모님 소득·재산 관련 정보를
선택적으로 추가 입력할 수 있다.

해당 정보를 모르거나 입력하지 않는 경우에는
추가 확인이 필요한 조건으로 처리한다.


#### STEP 3. 관련 정책 검색

AI Agent가 사용자 상황을 분석하고
필요한 정책 검색 도구를 호출한다.

RAG는 저장된 공식 정책정보를 검색하여
관련 정책과 근거 자료를 제공한다.

#### STEP 4. 자격 조건 진단

사용자 정보와 정책별 자격요건을 비교한다.

각 조건의 결과는 다음과 같이 표시한다.

- 충족
- 미충족
- 추가 확인 필요

예시:
- 연령: 충족
- 지역: 충족
- 소득: 추가 확인 필요

명확한 수치와 조건은 규칙 기반으로 비교한다.
복잡한 정책 문구의 해석은 AI가 보조한다.

정보가 부족하거나 조건이 불명확하면
자격을 임의로 확정하지 않는다.


#### STEP 5. 맞춤형 혜택 포트폴리오 추천

서비스는 사용자의 상황과 관련된 정책을
최대 5개까지 함께 추천한다.

다음 요소를 고려하여 추천 우선순위를 정한다.

- 사용자 관심 분야와의 관련성
- 확인된 자격 조건의 적합성
- 명확한 미충족 조건의 존재 여부
- 추가 확인이 필요한 조건
- 공식적으로 확인된 신청 가능 기간

명확히 미충족된 정책은 적합한 혜택으로
추천하지 않고 별도로 구분한다.

추천 결과에는 정책별 추천 이유와
자격 진단 요약 및 공식 근거를 표시한다.

여러 혜택을 함께 추천하는 것은
모든 정책을 동시에 수급할 수 있다는 의미가 아니다.

정책 간 중복 수혜 제한 분석은 공식 근거가
확인되는 경우에 한해 추가 구현을 검토한다.


#### STEP 6. 신청 준비사항 안내

사용자가 추천 정책을 선택하면 다음을 안내한다.

- 정책명 및 지원 내용
- 확인된 신청기간
- 신청 방법 및 공식 안내 URL
- 공식 자료에서 확인된 준비서류
- 추가 확인이 필요한 자격 조건

공식 자료에 없는 정보는 생성하지 않는다.

### 5.3 핵심 사용자 시나리오

사용자 A는 창원시에 거주하는
25세 취업준비생이다.

현재 자취 중이며 월세 부담을 줄일 수 있는
청년 지원정책을 찾고 있다.

사용자는 AI 혜택 코치에 자신의 상황을 입력한다.

AI는 입력 내용을 분석하여 주거비 지원과 관련된
청년정책을 검색한다.

서비스는 각 정책의 자격 조건을 비교하고
확인된 조건과 추가 확인이 필요한 조건을 보여준다.

사용자는 추천된 정책의 근거를 확인하고
필요한 신청 준비사항을 파악할 수 있다.

### 5.4 자격 진단 카드

정책별 결과를 이해하기 쉽게
자격 진단 카드 형태로 제공한다.

표시 항목:

- 정책명
- 지원 내용 요약
- 추천 이유
- 조건별 자격 진단 결과
- 추가 확인이 필요한 정보
- 신청기간 및 모집상태
- 공식 출처
- 신청 준비사항

자격 진단은 참고용으로 제공하며,
최종 자격은 해당 기관에서 확인해야 한다.

## 6. 서비스 범위

### 6.1 초기 개발 범위(MVP)


본 프로젝트는 제한된 개발 기간을 고려하여
자연어 기반 청년정책 검색, 자격 진단 및
맞춤형 혜택 포트폴리오 추천에 집중한다.

초기 서비스에서는 사용자와 관련된 청년정책을
최대 5개까지 함께 추천하고, 정책별 추천 이유와
신청 준비사항을 안내한다.

혜택 포트폴리오는 여러 정책을 함께 보여주는 기능이며,
동시 수급 가능성을 보장하지 않는다.

- 대상: 만 19~34세 청년
- 지역: 전국 공통 정책 및 경남·창원 지역정책
- 분야: 주거, 취업, 생활·자산형성
- 정책 데이터: 최초 20~40개 목표
- 추천 결과: 관련 정책 최대 5개
- 이용 형태: 웹 기반 서비스

정책별 실제 신청 대상과 연령 기준은
각 공식 공고를 따른다.

### 6.2 필수 구현 범위

본 프로젝트의 Must 기능은 총 8개이며,
기능 요구 명세서(REQUIREMENTS.md)와 동일하게 관리한다.

1. M01 - 자연어 상황 입력
2. M02 - 사용자 조건 추출·수정 및 필요 정보 보완
3. M03 - 공식 정책정보 기반 RAG 검색
4. M04 - AI Agent의 도구 선택 및 호출
5. M05 - 정책별 자격 진단 및 결과 카드
6. M06 - 맞춤형 혜택 포트폴리오 추천
7. M07 - 정책 상세정보 및 신청 준비 안내
8. M08 - 웹서비스 배포 및 전체 기능 통합

부모님 소득·재산 관련 정보는 해당 정책에서
요구하는 경우에만 선택적으로 입력받는다.

입력 정보가 부족하거나 공식 기준이 명확하지 않으면
'추가 확인 필요'로 표시한다.

모든 Must 기능은 배포된 서비스에서
정상적으로 연결되는 것을 완료 기준으로 한다.



### 6.3 추가 구현 검토 범위

추가 기능은 Should와 Could로 구분한다.

#### Should (우선 추가 검토)

- 공식 근거 기반 중복 수혜 가능성 분석
- 정책 간 중복 수혜 제한 사유 표시
- 확인된 조건을 바탕으로 한 혜택 조합 추천
- 공식 지원금액 기반 제한적 금액 비교

#### Could (선택적 확장)

- 나이·소득 변화에 따른 혜택 절벽 분석
- Long-term Memory 기반 개인화
- 관심 정책 및 신청 마감 알림
- 최적 혜택 조합과 총 수혜액 계산
- 교육·장학 분야 확대

Should와 Could는 Must 기능이 정상 작동하고
개발 일정에 여유가 있을 경우에만 검토한다.

공식 근거가 부족한 상태에서는
중복 수혜 가능성이나 예상 지원금액을
확정적으로 안내하지 않는다.


### 6.4 초기 개발 제외 범위

다음 기능은 초기 버전에서 구현하지 않는다.

- 정부 지원정책 자동 신청
- 실제 수급 자격 최종 확정
- 주민등록번호 등 민감한 식별정보 수집
- 전국 모든 지자체의 모든 정책 수집
- 모든 연령층을 대상으로 한 정책 추천
- 정부기관 인증 시스템 직접 연동
- 정책 조건에 근거가 없는 AI 임의 판단

### 6.5 서비스 운영 원칙

1. 공식 정책정보를 우선 활용한다.
2. 추천 결과에 공식 출처를 표시한다.
3. 정책 데이터의 마지막 확인일을 관리한다.
4. 신청기간이 불명확하면 확인 필요로 안내한다.
5. AI 생성 콘텐츠임을 명확하게 표시한다.
6. 개인정보는 서비스에 필요한 범위에서만 처리한다.
7. 입력되지 않은 자격 조건은 추정하지 않는다.
8. 최종 자격과 신청 가능 여부는 공식 기관 확인을 안내한다.

### 6.6 범위 변경 관리

프로젝트의 세부 구현 범위는 팀 회의를 통해
검토하고 합의한 후 최종 확정한다.

추가 기능은 핵심 기능의 개발 및 테스트에
영향을 주지 않는 경우에만 도입한다.

기능 변경 사항은 GitHub Issue와 문서에 기록한다.

## 7. AI 기술 활용 계획

### 7.1 AI 기술 도입 목적

본 프로젝트는 단순한 조건 검색 서비스가 아니라,
사용자의 자연어 상황을 이해하고 공식 정책정보를
바탕으로 자격 조건을 분석하는 AI 코치를 목표로 한다.

이를 위해 다음 두 가지 AI 기술을 필수로 적용한다.

- RAG (검색 증강 생성)
- AI Agent (도구 활용형 AI)

### 7.2 RAG 구조

RAG는 공식 청년정책 데이터를 검색하여
생성형 AI가 근거 있는 답변을 작성하도록 지원한다.

처리 과정:

1. 정부 및 공공기관의 정책 데이터를 확보한다.
2. 정책명, 지원 대상, 신청조건, 지원내용 등을 정리한다.
3. 정책 설명과 원문을 검색 가능한 형태로 저장한다.
4. 사용자 상황과 관련된 정책정보를 검색한다.
5. 검색된 공식 정보를 AI에 전달한다.
6. AI가 해당 근거를 바탕으로 답변을 생성한다.

정책의 연령, 지역, 소득 등 구조화된 조건은
별도 데이터 필드로 관리하고 규칙 기반으로 비교한다.

RAG는 특히 정책의 상세 설명, 예외 조건,
신청 절차 등의 근거를 검색하는 데 활용한다.

### 7.3 AI Agent 구조

AI Agent는 사용자의 요청을 분석하고
필요한 도구(Tool)를 선택하여 호출한다.

주요 도구:

1. search_policies
   - 사용자 조건과 관심 분야에 맞는 정책 검색

2. get_policy_detail
   - 특정 정책의 상세정보 및 공식 출처 조회

3. check_eligibility
   - 사용자 조건과 정책 자격요건 비교

4. get_application_guide
   - 신청기간, 신청 방법 및 준비사항 조회

AI Agent는 필요한 도구를 선택하고 결과를 조합한다.

각 도구가 조회하거나 판단한 결과와
AI가 생성한 설명은 구분하여 처리한다.

### 7.4 자격 진단 로직

자격 조건 진단은 정확성을 높이기 위해
규칙 기반 비교와 AI의 설명 기능을 분리한다.

규칙 기반으로 비교 가능한 항목:

- 연령
- 거주지역
- 소득 수치(공식 기준이 명확한 경우)
- 취업 상태(정책 조건이 구조화된 경우)
- 신청기간

진단 상태:

- 충족
- 미충족
- 추가 확인 필요

정책 조건에 필요한 정보가 입력되지 않았거나,
공식 기준을 명확히 확인할 수 없는 경우에는
'추가 확인 필요'로 표시한다.

AI는 규칙 기반 진단 결과를 임의로 변경하지 않고
판단 근거를 이해하기 쉽게 설명한다.

### 7.5 맞춤형 추천 구조

정책 추천 시 다음 요소를 고려한다.

- 사용자 관심 분야와의 관련성
- 정책별 확인된 자격 조건
- 명확하게 미충족된 조건의 존재 여부
- 추가 확인이 필요한 조건
- 공식적으로 확인된 신청기간

추천 우선순위는 사전에 정의한 기준으로 계산하며,
AI는 추천된 이유를 자연어로 설명한다.

조건이 불명확한 정책을
'신청 가능 확정'으로 표시하지 않는다.

### 7.6 AI 안전장치

1. 공식 출처가 확인된 정책만 추천한다.
2. 정책에 없는 자격 조건을 생성하지 않는다.
3. 사용자가 제공하지 않은 조건은 추정하지 않는다.
4. AI가 규칙 기반 진단 결과를 임의로 변경하지 않는다.
5. 정보가 충돌하거나 부족하면 추가 확인을 안내한다.
6. 정책별 출처 URL과 마지막 확인일을 표시한다.
7. AI 생성 답변임을 화면에 명시한다.
8. 최종 수급 자격은 해당 기관에서 확인하도록 안내한다.

### 7.7 추가 기술 검토

필수 기능 완성 후 개발 여력이 있을 경우
다음 기술을 추가 검토한다.

- Long-term Memory: 관심 정책 및 이전 조건 저장
- 자동화 워크플로우: 신청 마감 알림

해당 기능은 초기 Must 범위에 포함하지 않는다.

## 8. 데이터 수집 및 관리 계획

### 8.1 데이터 수집 목표

본 프로젝트는 공식 청년정책 정보를 기반으로
신뢰할 수 있는 맞춤형 정책 추천을 제공한다.

초기 목표 데이터는 20~40개 정책이다.

정책 수를 무리하게 늘리기보다
자격 조건과 출처가 검증된 데이터를 우선한다.

### 8.2 주요 데이터 출처

1. 온통청년
   - 청년정책 OPEN API
   - 공식 청년정책 상세정보

2. 정부24 및 공공데이터포털
   - 공식 공공서비스 정보
   - 필요 시 보완 데이터로 활용

3. 경상남도 및 창원시 공식 홈페이지
   - 지역 청년정책
   - 신청기간 및 자격 조건 검증

### 8.3 온통청년 API 신청 현황

- 신청일: 2026-10-24
- 신청자 유형: 개인
- 신청 API: 청년정책API
- 현재 상태: 신청 접수 (승인 대기)

API 승인 후 다음 사항을 확인한다.

1. 인증키 발급 여부 및 유효기간
2. 실제 API 호출 가능 여부
3. 정책 데이터 제공 항목
4. 요청 제한 및 이용 조건
5. 데이터 갱신 방식

API 승인 전에는 공식 출처로 검증한
소규모 정책 데이터를 활용할 수 있도록 준비한다.

### 8.4 정책 데이터 관리 항목

정책별로 다음 정보를 관리한다.

- 정책 고유 ID
- 정책명
- 운영 기관
- 지원 지역
- 지원 분야
- 지원 내용
- 연령 조건
- 소득 조건
- 취업 및 주거 관련 조건
- 신청 시작일 및 마감일
- 신청 방법
- 공식 출처 URL
- 마지막 확인일
- 데이터 출처
- 가구 구성 및 원가구 관련 자격 조건
- 부모님 소득·재산 조건의 적용 여부
- 추가 확인이 필요한 자격 조건
- 공식적으로 확인된 중복 수혜 제한 사항
- 중복 수혜 제한 관련 근거 및 출처

가구 및 부모님 관련 정보는 정책에서 요구하는
자격 조건을 관리하기 위한 항목이다.

사용자가 입력하는 실제 부모님 소득·재산 정보는
초기 서비스에서 영구 저장하지 않는 것을 원칙으로 한다.

중복 수혜 제한 정보는 공식 근거가 확인된 경우에만
관리하며, 해당 정보를 활용한 자동 분석 기능은
Should 범위에서 검토한다.


공식 자료에 명시되지 않은 항목은
임의로 채우지 않고 미확인 상태로 관리한다.

### 8.5 데이터 처리 과정

1. 공식 API 또는 공고에서 정책정보 수집
2. 원본 데이터 보관 및 출처 기록
3. 서비스 내부 데이터 구조로 정규화
4. 중복 정책 확인 및 통합
5. 정책 자격 조건의 구조화
6. RAG 검색을 위한 문서 저장 및 색인
7. 검증된 정책정보를 서비스에 제공

데이터 수집과 검색은 가능한 범위에서 자동화하되
초기 데이터의 정확성은 팀원이 직접 확인한다.

### 8.6 데이터 최신성 관리

청년 지원정책은 신청기간과 자격 조건이
변경될 수 있으므로 최신성 관리가 중요하다.

이를 위해 다음 원칙을 적용한다.

- 데이터별 마지막 확인일 기록
- 모집상태를 확인할 수 없으면 확인 필요 표시
- 신청기간이 지난 정책은 별도 표시하거나 제외
- 공식 출처의 내용과 차이가 발견되면 재검증
- API 오류 시 오래된 정보를 최신 정보로 표현하지 않음

### 8.7 개인정보 보호

초기 서비스는 개인정보 수집을 최소화한다.

- 회원가입 없이 핵심 기능 이용 가능하도록 설계
- 주민등록번호 등 고유식별정보 수집 제외
- 사용자 입력은 필요한 목적에 한해 처리
- 불필요한 원문 대화 및 개인정보 로그 저장 제한
- 저장이 필요한 정보는 접근 권한과 보관기간 관리
- 외부 AI 서비스로 전달되는 정보 최소화
- 개인정보 처리 및 AI 사용 사실 안내

### 8.8 데이터 관련 위험 및 대응

#### 위험 1. API 승인 지연

대응:
공식 정책 페이지에서 확인한 데이터로
초기 검색 및 진단 기능을 개발한다.

#### 위험 2. 정책별 자격 조건 형식 차이

대응:
공통적으로 비교 가능한 조건부터 구조화하고
복잡한 예외 조건은 추가 확인 필요로 표시한다.

#### 위험 3. 정책정보 변경

대응:
출처와 확인일을 기록하고
모집상태를 임의로 확정하지 않는다.

#### 위험 4. AI의 잘못된 자격 판단

대응:
명확한 조건은 규칙 기반으로 비교하고,
AI는 근거 설명 및 추가 질문 생성에 활용한다.

## 9. 주요 기능 및 우선순위

### 9.1 기능 우선순위 기준

본 프로젝트는 MoSCoW 방식으로 기능 우선순위를 구분한다.

- Must: 최종 평가 전 반드시 구현하고 검증할 기능
- Should: 필수 기능 완성 후 우선적으로 추가할 기능
- Could: 개발 일정에 여유가 있을 경우 검토할 기능
- Won't: 이번 프로젝트에서 구현하지 않을 기능

Must 기능은 개별 버튼이나 API 단위가 아닌
사용자 워크플로우 단위로 정의한다.

### 9.2 Must 기능

| ID | 기능 | 완료 기준 |
|---|---|---|
| M01 | 자연어 상황 입력 | PC·모바일에서 자연어 입력 및 분석 요청 가능 |
| M02 | 조건 추출 및 보완 | 조건 추출·수정, 필요한 가구 정보 선택 입력 가능 |
| M03 | RAG 정책 검색 | 실제 공식 정책과 근거 문서를 검색하여 답변에 활용 |
| M04 | AI Agent | 요청에 따라 실제 검색·상세조회 도구 호출 |
| M05 | 자격 진단 및 결과 카드 | 충족·미충족·추가 확인 필요를 근거와 함께 표시 |
| M06 | 혜택 포트폴리오 | 관련 정책을 최대 5개 추천하고 이유 표시 |
| M07 | 신청 준비 안내 | 정책 상세, 신청기간 및 공식 출처 안내 |
| M08 | 서비스 배포 및 통합 | 외부에서 전체 핵심 사용자 흐름 정상 작동 |

Must 기능의 상세 요구사항과 테스트 기준은
docs/REQUIREMENTS.md를 기준으로 관리한다.

모든 Must 기능은 개별 동작뿐 아니라
전체 사용자 흐름에서도 정상 작동해야 한다.

### 9.3 Should 기능

- 공식 근거 기반 중복 수혜 가능성 분석
- 정책 간 중복 수혜 제한 사유 표시
- 근거가 확인된 혜택 조합 추천
- 공식 지원금액 기반 제한적 금액 비교

### 9.4 Could 기능

- 나이·소득 변화에 따른 혜택 절벽 분석
- Long-term Memory 기반 개인화
- 관심 정책 및 신청 마감 알림
- 최적 혜택 조합 및 총 수혜액 계산
- 교육·장학 분야 확장

### 9.5 Won't 기능

- 정부 정책 자동 신청 및 제출
- 최종 수급 자격 확정
- 주민등록번호 등 고유식별정보 수집
- 전국 모든 정책 실시간 수집
- 공공기관 인증 시스템 직접 연동

### 9.6 Must 기능 검증 원칙

Must 기능별로 최소 1개 이상의 정상 테스트를
준비하고, 전체 사용자 흐름을 통합 테스트한다.

주요 검증 사례:

1. 자연어에서 주요 조건을 추출하는가?
2. 입력되지 않은 정보를 임의로 추정하지 않는가?
3. 공식 정책정보와 출처를 검색하는가?
4. AI Agent가 실제 도구를 호출하는가?
5. 자격 조건을 올바르게 분류하는가?
6. 미충족 정책을 적합하다고 안내하지 않는가?
7. 신청 준비사항에 없는 정보를 생성하지 않는가?
8. 모바일 및 PC에서 결과를 확인할 수 있는가?
9. 배포 URL에서 핵심 기능이 정상 동작하는가?

## 10. 시스템 구성 계획

### 10.1 전체 시스템 구조

본 서비스는 다음 구성요소를 중심으로 개발한다.

1. Frontend
   - 자연어 입력 화면
   - 사용자 조건 확인 및 수정 화면
   - 추천 정책 목록
   - 자격 진단 카드 및 상세정보 화면
   - 부모님 및 가구 정보 선택 입력 화면
   - 맞춤형 혜택 포트폴리오 결과 화면

2. Backend
   - 사용자 요청 처리
   - 정책 검색 및 추천 API
   - AI Agent 실행
   - 자격 진단 로직
   - 데이터 조회 및 관리
   - 포트폴리오 추천 결과 처리
   - 부모님 및 가구 관련 조건 진단

3. AI 서비스
   - 자연어 조건 추출
   - RAG 기반 정책 근거 검색
   - Agent의 도구 선택 및 호출
   - 추천 이유 및 신청 안내 생성

4. Database
   - 정책 기본정보
   - 정책별 자격 조건
   - 공식 출처 및 확인일
   - RAG 검색용 정책 문서
   - 가구 및 원가구 관련 정책 자격 조건
   - 공식 근거가 확인된 중복 수혜 제한 정보

5. 외부 데이터
   - 온통청년 청년정책API
   - 정부 및 지자체 공식 정책정보

### 10.2 권장 기술 스택

기술 스택은 팀 회의에서 최종 확정한다.

| 영역 | 권장 기술 |
|---|---|
| Frontend | HTML, CSS, JavaScript |
| Backend | Python, FastAPI |
| AI 모델 | API 기반 생성형 AI |
| AI Agent | Tool Calling |
| RAG | 정책 문서 검색 + 생성형 AI |
| Database | PostgreSQL |
| 벡터 검색 | pgvector 또는 경량 벡터 저장소 |
| 배포 | Render 등 외부 접속 가능한 플랫폼 |
| 협업 | Git, GitHub |

초기 정책 데이터 규모가 작으므로
복잡한 AI 인프라를 도입하지 않는다.

RAG는 정책 문서의 근거를 검색하는 구조로 구현하고,
정확한 자격 조건 비교에는 구조화된 데이터를 사용한다.

### 10.3 주요 데이터 구조

#### policies
정책 기본정보를 저장한다.

- id
- title
- organization
- region
- category
- description
- application_start
- application_end
- source_url
- verified_at

#### policy_conditions
정책별 자격 조건을 저장한다.

- id
- policy_id
- condition_type
- operator
- condition_value
- evidence_text
- household_condition_type
- parent_income_required
- parent_asset_required
- additional_verification_required


#### policy_documents
RAG 검색에 사용할 정책 설명을 저장한다.

- id
- policy_id
- content
- source_url
- updated_at

#### policy_restrictions (추가 설계 검토)

정책 간 중복 수혜 제한 사항을
공식 근거와 함께 관리하기 위한 구조이다.

- id
- policy_id
- related_policy_id
- restriction_type
- evidence_text
- source_url
- verified_at

※ 해당 구조는 Should 기능 구현을 위한
설계 제안이며, 실제 테이블 생성 여부는
팀원들과 협의하여 결정한다.


실제 테이블 구조는 개발 과정에서 조정한다.

### 10.4 주요 API 구조

| Method | Endpoint | 역할 |
|---|---|---|
| POST | /api/analyze | 자연어 조건 추출 |
| POST | /api/recommend | 정책 검색 및 추천 |
| GET | /api/policies | 정책 목록 조회 |
| GET | /api/policies/{id} | 정책 상세 조회 |
| POST | /api/eligibility | 정책별 자격 진단 |
| GET | /api/health | 서비스 상태 확인 |

해당 API는 설계 초안이며,
실제 개발 시 필요에 따라 통합하거나 변경한다.

### 10.5 주요 화면

#### 화면 1. 메인 화면
- 서비스 소개
- 자연어 상황 입력창
- 입력 예시

#### 화면 2. 조건 확인 화면
- AI가 추출한 조건 표시
- 사용자 조건 수정
- 부족한 정보 안내
- 정책상 필요한 가구·부모님 정보 선택 입력
- 모르는 정보는 건너뛰기 가능

#### 화면 3. 추천 결과 화면
- 추천 정책 3~5개
- 추천 이유
- 조건별 자격 진단 카드
- 여러 혜택을 함께 보여주는 포트폴리오 UI
- 동시 수혜 가능성을 보장하지 않는다는 안내

#### 화면 4. 정책 상세 화면
- 지원 내용
- 자격 조건
- 신청기간 및 신청 방법
- 준비사항
- 공식 출처 링크

### 10.6 자격 진단 카드 UI

정책별 자격 진단 카드는 다음 요소로 구성한다.

- 정책명과 지원 내용
- 사용자와 정책의 관련성 설명
- 연령: 충족 / 미충족 / 추가 확인 필요
- 지역: 충족 / 미충족 / 추가 확인 필요
- 소득: 충족 / 미충족 / 추가 확인 필요
- 취업 상태: 충족 / 미충족 / 추가 확인 필요
- 기타 정책별 조건
- 추가 확인이 필요한 항목
- 공식 출처 및 마지막 확인일

자격 진단 결과는 근거가 확인된 범위에서만 제공한다.

화면에는 다음 안내를 표시한다.

"AI가 제공하는 분석은 참고용이며,
최종 신청 자격과 최신 조건은 공식 기관에서
확인해야 합니다."

### 10.7 보안 및 안정성

- 외부 AI 및 정책 API 키는 환경변수로 관리한다.
- 인증키와 개인정보를 GitHub에 업로드하지 않는다.
- 외부 API 오류 시 오류 안내를 제공한다.
- 정책 검색 실패 시 존재하지 않는 정보를 생성하지 않는다.
- 정책 데이터가 오래된 경우 확인일을 표시한다.
- 평가자가 테스트할 수 있도록 기본 입력 예시를 제공한다.

## 11. 팀 구성 및 개발 일정

### 11.1 팀 구성

본 프로젝트는 조장을 포함한 5명이 참여하는
팀 프로젝트로 진행한다.

모든 팀원은 개발, 테스트, 데이터 관리, 문서 작성 등
실질적인 작업을 담당하고 GitHub에 기여 기록을 남긴다.

팀원별 역할은 첫 팀 회의에서 협의하여 정했으며,
세부 구현 범위는 공통 코드 구조를 확인한 후
필요에 따라 조정한다.


### 11.2 팀원별 역할 분담

| 담당자 | 역할 | 주요 업무 |
|---|---|---|
| 조장 | 프로젝트 총괄·통합 | 일정 및 범위 관리, 기능 통합, 배포, 품질 검증 |
| 이현서 | Frontend | 자연어 입력, 조건 수정, 혜택 포트폴리오 및 자격 진단 카드 UI |
| 김하정 | Backend | FastAPI, 정책 조회 API, 규칙 기반 자격 진단, 추천 로직 |
| 탁서윤 | AI/RAG | 자연어 조건 추출, RAG 검색, AI Agent 및 근거 기반 설명 |
| 윤정찬 | Database | DB 설계, 공식 정책 데이터 수집·정제, 자격 조건과 출처 관리 |

각 팀원은 담당 기능의 코드, 데이터,
테스트 결과 및 관련 문서를 관리한다.

조장은 프론트엔드, 백엔드, AI, 데이터베이스의
연동 상태를 점검하고 전체 기능을 통합한다.

세부 구현 업무는 공통 코드 뼈대와 API·DB 구조를
확인한 후 팀원 협의를 통해 조정할 수 있다.

기능별 주 담당자와 협업 관계는
docs/REQUIREMENTS.md의 7장을 참고한다.

모든 팀원의 실제 작업 결과는
GitHub Issue, Commit, Pull Request 등으로 기록한다.


### 11.3 GitHub 협업 방식

- GitHub 저장소를 공통 작업 공간으로 사용한다.
- 작업은 GitHub Issue로 등록하고 담당자를 지정한다.
- 각 팀원은 별도 브랜치에서 작업한다.
- 기능 구현 후 Pull Request를 생성한다.
- 다른 팀원이 변경사항을 검토한 후 병합한다.
- main 브랜치는 배포 가능한 상태를 유지한다.
- 주요 결정과 변경사항을 문서에 기록한다.

권장 브랜치 이름:

- feature/frontend
- feature/backend
- feature/rag-agent
- feature/policy-data
- docs/project-plan

실제 브랜치는 작업별로 구분하여 생성한다.

프로젝트 제출 마감일은 2026년 11월 25일이다.

핵심 기능의 구현을 우선하며,
일정이 지연될 경우 Should 및 Could 기능을 축소한다.

### 11.5 사용자 테스트 계획

실제 타깃 사용자 5명 이상을 대상으로
서비스를 테스트한다.

테스트 항목:

1. 자연어 입력이 이해하기 쉬운가?
2. 사용자 조건이 정확하게 추출되는가?
3. 추천 정책이 실제 상황과 관련 있는가?
4. 자격 진단 결과를 이해할 수 있는가?
5. 추천 근거와 공식 출처를 확인할 수 있는가?
6. 신청 준비사항이 실질적으로 도움이 되는가?

테스트 과정에서 발견된 문제를 기록하고
우선순위에 따라 개선한다.

피드백 문서는 docs 디렉터리에서 관리한다.

개인정보가 포함되지 않도록
테스트 참여자 정보는 익명화한다.

### 11.6 팀 운영 원칙

- 조장은 일정과 작업 진행 상황을 관리한다.
- 중요한 기술 및 범위 변경은 팀 회의에서 결정한다.
- 모든 팀원은 자신의 작업 결과를 공유한다.
- 담당 작업은 GitHub Issue와 연결한다.
- 통합 테스트는 팀원 전체가 참여한다.
- 일정 변경과 위험 요소는 즉시 공유한다.

## 12. 기대 효과 및 평가 대응

### 12.1 기대 효과

#### 사용자 관점

- 청년 지원정책 탐색에 필요한 부담 감소
- 복잡한 자격 조건에 대한 이해 향상
- 사용자 상황에 맞는 정책을 우선 확인 가능
- 신청 전 필요한 조건과 준비사항 파악

#### 기술적 관점

- 생성형 AI를 활용한 자연어 조건 추출
- RAG 기반 공식 정책정보 검색
- AI Agent의 도구 선택 및 호출
- 규칙 기반 자격 진단과 AI 설명의 결합
- 출처와 근거가 표시되는 정책 추천

#### 팀 프로젝트 관점

- 5인 협업 개발 경험 확보
- GitHub Issue 및 Pull Request 기반 협업
- 실제 서비스 배포 경험
- 사용자 피드백 기반 개선 경험

### 12.2 평가 대응 전략

본 프로젝트는 평가자가 배포 서비스와
GitHub 문서를 직접 확인할 수 있도록 준비한다.

주요 대응 원칙:

1. 생성형 AI를 핵심 기능에 활용한다.
2. RAG와 AI Agent가 실제로 동작하도록 구현한다.
3. Must 기능을 모두 테스트하고 정상 동작을 확인한다.
4. 외부에서 접근 가능한 배포 URL을 제공한다.
5. 실제 사용자 5명 이상의 테스트를 수행한다.
6. 사용자 피드백과 개선 내용을 기록한다.
7. 팀원 5명의 실질적인 기여 기록을 관리한다.
8. AI 생성 콘텐츠를 명확하게 표시한다.
9. 개인정보를 최소한으로 수집하고 안전하게 처리한다.
10. 평가자가 쉽게 따라 할 수 있는 테스트 방법을 제공한다.

### 12.3 평가 기준 G1~G7 대응

평가 기준별 세부 내용은 공식 평가표를 기준으로
최종 확인하고 문서에 반영한다.

| 구분 | 프로젝트 대응 내용 |
|---|---|
| G1 | 프로젝트 문제 정의 및 AI 활용 필요성 |
| G2 | RAG와 AI Agent 핵심 기술 적용 |
| G3 | Must 기능 구현 및 정상 동작 |
| G4 | 외부 접근 가능한 서비스 배포 |
| G5 | 실제 사용자 테스트와 피드백 개선 |
| G6 | GitHub 협업 및 팀원별 기여 기록 |
| G7 | 제출 문서와 평가자 테스트 환경 준비 |

※ 위 G1~G7 매핑은 임시 정리이며,
공식 평가 항목의 정확한 명칭과 내용은
평가 안내문 확인 후 수정한다.

### 12.4 최종 제출물

최종 제출물은 다음 6가지이다.

1. 프로젝트 기획서
   - docs/PROJECT_PLAN.md

2. 기능 요구 명세서
   - docs/REQUIREMENTS.md

3. 서비스 배포 URL 및 평가자 테스트 방법
   - README.md에 배포 URL과 테스트 절차 안내

4. GitHub 저장소 URL
   - 최종 제출 시 저장소 주소 제공

5. 사용자 피드백 기록
   - docs/USER_FEEDBACK.md

6. 발표 자료
   - docs 디렉터리에 최종 발표 자료 저장

### 12.5 평가자 테스트 시나리오

평가자가 별도의 사전 설명 없이도
서비스를 테스트할 수 있도록 준비한다.

기본 테스트 예시:

"나는 25살이고 창원에서 자취 중인 취준생이야.
월세가 부담돼."

예상 흐름:

1. 메인 화면에서 예시 문장 입력
2. AI가 추출한 사용자 조건 확인
3. 관련 청년정책 검색 실행
4. 추천 정책과 자격 진단 카드 확인
5. 추가 확인이 필요한 조건 확인
6. 추천 이유 및 공식 출처 확인
7. 신청 준비사항 확인

README에는 테스트 입력 예시와
정상 동작 확인 방법을 구체적으로 기록한다.
