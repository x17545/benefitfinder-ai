## 1. 프로젝트 개요

### 1.1 프로젝트명

AI 혜택 코치 (BenefitFinder AI). 화면 표시 이름은 청년 정책 매니저다.

### 1.2 프로젝트 소개

AI 혜택 코치는 사용자가 13단계 선택 입력으로 자신의 조건을 고르면, 구조화 DB 조건으로 관련 청년 지원정책을 검색하고 자격을 진단한 뒤 함께 받을 수 있는 지원금 조합 중에서 총액이 가장 큰 조합을 계산해 주는 서비스이다.

문장 입력과 챗봇 대화는 제공하지 않는다. 입력은 정해진 선택지로만 받고, 정제된 조건 비교와 조합 계산 순서는 분석 흐름 코드가 정한다.

(2026-10-28 바로잡음: 설계서 검토 결과 RAG/AI Agent 개념 없이 구현 가능한 서비스로 본다. F02는 정책 검색(구조화 DB 조건), F03은 분석 흐름·진행 상태(일반 application 코드)다. RAG/Agent/LLM/임베딩은 필수 아님, 후속 필요성 검증 전 기술 미정이며 설명은 판정 결과와 근거를 조합한 템플릿을 기본으로 한다.)

2026-10-27 추가 회의에 따라 첫 MVP는 청년 대상 취업·주거 혜택에 한정한다. 생활·자산형성·교육·장학 등 나머지 청년 분야와 다른 대상의 혜택은 scale up 단계에서 추가한다.

### 1.3 핵심 서비스 흐름

1. 시작 화면에서 이용 안내를 확인하고 필수 동의
2. 13단계 선택지로 조건 입력, 마지막 단계에서 요약 확인과 수정
3. 분석 흐름 코드가 순서대로 실행하며 분석 (진행 상황을 화면에 실시간 표시)
4. 정책 검색(구조화 DB 조건)과 조건별 자격 진단
5. 함께 받을 수 있는 조합 계산 (추천 1개와 대안 2개, 포기하는 지원금 표시)
6. 조합 속 지원금마다 자격 진단과 추천 이유, 신청하러 가기 연결
7. 상황이 바뀌면(취업, 소득 상승 등) 조합과 총액 변화, 실효한계세율 확인
8. 정책 상세에서 원문 근거와 신청 방법, 공식 출처 확인

### 1.4 핵심 기술

- 구조화 정책 검색: 공식 청년정책 데이터의 구조화 DB 조건 검색과 근거 인용
- 분석 흐름: 순서대로 실행하는 일반 application 코드, 진행 상황 실시간 전송
- 코드 계산: 자격 판정, 조합과 총액, 현재가치, 실효한계세율
- 판정 근거 템플릿 설명: 추천 이유 한 줄과 지금 할 일 설명 (RAG/Agent/LLM/임베딩은 필수 아님, 후속 필요성 검증 전 기술 미정)

### 1.5 프로젝트 목표

1. 선택 입력만으로 청년 지원정책을 쉽게 찾는다.
2. 사용자 조건과 정책 자격요건을 비교해 충족, 미충족, 확인 필요를 가린다.
3. 함께 받을 수 있는 조합 중에서 총액이 가장 큰 조합을 계산해 근거와 함께 보여 준다.
4. 실제 정책정보를 근거로 신뢰할 수 있는 답변을 제공한다.
5. 외부에서 사용할 수 있는 웹서비스를 완성한다.
6. 신청 준비와 다음 행동까지 연결한다.

분석 결과의 진단은 최종 수급 자격을 확정하지 않는다. 최종 자격과 신청 조건은 공식 기관 안내를 확인한다.

## 2. 추진 배경과 문제 정의

### 2.1 추진 배경

정부와 지방자치단체에서는 청년을 대상으로 주거, 취업, 생활안정 등 다양한 지원정책을 운영하고 있다. 정책이 여러 기관과 웹사이트에 분산되어 있고 정책마다 신청 대상과 자격 조건이 달라, 사용자가 자신에게 맞는 정책을 찾기 어렵다.

청년들은 본인 생활 상황을 정책 검색 조건으로 바꾸거나 복잡한 자격요건을 해석하는 과정에서 어려움을 겪는다. 이에 정책 원문을 분석·정제해 조건과 근거를 구조화하고, 공식 정책정보를 바탕으로 맞춤형 혜택 조합을 계산하는 서비스를 만든다.

### 2.2 기존 서비스의 한계

기존 청년정책 플랫폼에서도 정책 검색, 조건별 조회, AI 상담, 자격 진단 등을 제공한다. 그러나 어떤 정책이 있는지를 알려 주는 데 그치고, 어떤 지원금 조합을 받는 것이 가장 이득인지를 계산해 주지는 않는다.

본 프로젝트는 정책 목록 제공을 넘어, 중복 수혜 제한을 반영한 조합 계산과 총액 비교, 상황 변화 시뮬레이션까지 하나의 사용자 경험으로 연결한다.

### 2.3 해결하고자 하는 문제

1. 사용자가 자신에게 필요한 정책을 찾기 어렵다.
2. 정책별 자격 조건이 복잡하여 이해하기 어렵다.
3. 여러 정책 중 무엇을 우선 확인할지 판단하기 어렵다.
4. 정책이 추천된 이유와 부족한 조건을 파악하기 어렵다.
5. 신청 전 확인사항과 준비서류를 찾는 과정이 번거롭다.
6. 함께 받을 수 있는 조합과 총액을 비교하기 어렵다.

### 2.4 제안하는 해결 방법

1. 13단계 선택 입력으로 사용자 조건을 구조화한다.
2. 공식 청년정책 데이터에서 관련 정책을 검색한다.
3. 사용자 조건과 정책별 자격요건을 비교한다.
4. 조건별 충족, 미충족, 확인 필요를 표시한다.
5. 중복 수혜 제한을 반영해 총액이 가장 큰 조합을 계산한다.
6. 포기하는 지원금과 현재가치, 실효한계세율을 함께 보여 준다.
7. 추천 근거와 추가 확인사항, 신청 준비사항을 안내한다.

분석 결과는 참고용이며 최종 신청 자격을 확정하지 않는다.

### 2.5 기존 서비스와의 차별점

- 선택 입력과 단계별 정책정보 조회 결합
- 구조화 DB 조건 기반 공식 정책정보 근거 인용
- 조건별 근거를 제시하는 자격 진단
- 중복 제한 반영 최적 조합 계산과 총액 비교
- 상황 변화 시뮬레이션과 실효한계세율 안내
- 추천부터 신청 준비까지 연결되는 통합 경험

## 3. 프로젝트 목표

### 3.1 핵심 목표

사용자가 선택 입력으로 조건을 고르면 구조화 DB 조건으로 관련 청년정책을 검색하고, 자격을 분석한 뒤 신청 준비까지 안내하는 웹서비스를 구현한다. 단순 검색을 넘어, 어떤 조합이 가장 이득인지를 숫자로 계산해 보여 주는 것을 핵심으로 한다.

### 3.2 세부 목표

1. 선택 입력 기반 사용자 조건 수집
   - 13단계 선택지와 구간 입력으로 조건을 받는다.
   - 입력되지 않은 정보는 임의로 추정하지 않는다.
2. 공식 정책정보 기반 검색
   - 정부와 공공기관 정책 데이터를 활용한다.
   - 구조화 DB 조건으로 관련 정책의 근거를 검색한다.
3. 조건별 자격 진단
   - 정책 조건과 사용자 정보를 비교한다.
   - 충족, 미충족, 확인 필요로 구분한다.
   - 판단 근거를 함께 제공한다.
4. 최적 조합 계산
   - 중복 수혜 제한을 반영해 총액 최대 조합을 구한다.
   - 추천 1개와 대안 2개를 총액과 함께 비교한다.
   - 포기하는 지원금과 현재가치를 표시한다.
5. 상황 변화 분석
   - 취업, 소득 상승 등 조건 변화 시 조합과 총액 변화를 보여 준다.
   - 실효한계세율과 혜택 절벽을 안내한다.
6. 신청 준비 안내
   - 신청기간, 신청 방법, 준비사항을 안내한다.
   - 공식 신청 페이지와 정책 원문을 연결한다.
7. 실제 사용 가능한 서비스 완성
   - 외부 접속 가능한 웹서비스로 배포한다.
   - 최소 5명의 실제 사용자 테스트를 진행한다.
   - 사용자 피드백을 반영하여 개선한다.

### 3.3 프로젝트 성공 기준

- 13단계 선택 입력으로 조건을 수집할 수 있다.
- 실제 정책 데이터를 검색하여 조합을 계산할 수 있다.
- 정책별 자격 조건과 판단 근거를 표시할 수 있다.
- 정보가 부족할 때 추가 확인이 필요함을 안내한다.
- 추천 조합의 공식 출처를 확인할 수 있다.
- 외부에서 서비스에 접속하고 핵심 기능을 이용할 수 있다.
- 사용자 5명 이상의 테스트와 피드백 기록을 확보한다.
- 팀원 5명의 실질적인 개발과 문서 기여를 기록한다.

## 4. 타깃과 범위

### 4.1 주요 타깃

만 19세부터 39세까지의 청년 개인이다. 기업과 소상공인 정책은 다루지 않는다. 나이가 범위를 벗어나면 받을 수 있는 것이 적을 수 있음을 안내하고 막지 않는다.

### 4.2 세부 사용자 유형

- 유형 A. 취업준비생: 구직활동 지원과 주거비 부담 완화가 필요하다.
- 유형 B. 대학생: 청년 주거 지원과 취업 준비 혜택을 확인한다.
- 유형 C. 사회초년생: 청년 취업·주거 지원을 확인한다. 자산형성 혜택은 확장 단계에서 지원한다.
- 유형 D. 기혼 청년: 부모님 입력을 생략하고 정책별 면제 근거와 필요한 본인 가구 조건을 확인한다.
- 유형 E. 35세 이상: 군 복무 연장 인정 정책의 적용 여부를 함께 본다.

### 4.3 지원 지역과 분야

- 전국의 취업·주거 정책 중 연령 조건이 19세부터 39세와 겹치는 정책을 수집 대상으로 한다.
- 조합 계산에는 금액과 중복 제한, 지급 시점을 사람이 검수한 취업·주거 정책만 넣는다. 두 분야 안에서 30개 검수를 목표로 시작해 늘린다.
- 초기 분야는 취업과 주거다. 생활·자산형성·교육·장학 등은 확장 단계로 둔다.

### 4.4 대표 사용자 흐름

1. 시작 화면에서 조건 선택을 시작한다.
2. 나이, 지역, 상황, 학력, 혼인, 사는 형태, 집 계약, 소득과 재산, 해당 조건, 관심 분야, 받은 이력, 부모님 정보(선택), 최종 확인까지 13단계를 고른다.
3. 부모님 소득과 재산은 정책에 필요한 경우에만 선택 입력으로 묻는다. 기혼이면 묻지 않는다. 모르거나 건너뛴 값은 미입력으로 두고 확인 필요로 처리한다.
4. 로딩 화면에서 도구별 진행 상황을 확인한다.
5. 추천 조합 1개와 대안 2개를 총액과 함께 비교한다.
6. 조합 속 정책을 눌러 자격 진단과 원문 근거, 신청 준비를 확인한다.
7. 상황이 바뀌면 화면에서 조합 변화를 확인한다.

### 4.5 사용자 기대 효과

- 정책을 찾는 검색 부담 감소
- 복잡한 자격 조건에 대한 이해 향상
- 가장 이득인 조합의 우선 확인
- 신청 전 조건과 준비 과정 파악

### 4.6 분야 확장 계획

첫 MVP 이후 생활·자산형성·교육·장학 등 다른 청년 분류를 먼저 추가할 수 있고, 다른 대상의 혜택으로도 넓힌다(scale up). 취업·주거는 `youth` 내 정책 분류로 관리하며 별도 앱이나 최상위 domain으로 분리하지 않는다. 확장 시 공통 혜택 처리와 분야별 조건의 경계를 유지하고, 아키텍처의 분야 추가 방식을 따른다. 상세는 [ARCHITECTURE.md](ARCHITECTURE.md)를 본다.

## 6. 데이터 수집과 관리 계획

### 6.1 데이터 수집 목표

공식 청년정책 정보를 바탕으로 신뢰할 수 있는 조합 계산을 제공한다. 수집은 전국의 청년 취업·주거 정책으로 한정하고, 검색·진단·조합·상황 변화·상세에도 같은 범위를 적용한다. 조합 계산에 쓰는 데이터는 검수된 것만 쓴다.

### 6.2 주요 데이터 출처

1. 온통청년 청년정책 API (주 출처)
2. 공공데이터포털 공공서비스, 보조금24 API (보완)
3. 한국은행 ECOS 기준금리 (현재가치 할인율)

두 정책 API에 없는 정책은 수집하지 않는다. 크롤링과 지자체 홈페이지 개별 수집은 하지 않는다.

### 6.3 검수와 조합 투입 기준

- 전체 수집: 연령 조건이 19세부터 39세와 겹치는 취업·주거 정책
- 검수 완료: 금액과 중복 제한, 지급 시점을 사람이 확인한 정책
- 조합 계산에는 검수 완료된 취업·주거 정책만 넣는다. 두 분야 안에서 30개 검수를 목표로 시작해 늘리며, 실제 확보 수는 아직 검증하지 않았다.
- 검수 전 정책도 검색과 자격 진단, 정책 상세에서는 볼 수 있다.

### 6.4 정책 데이터 관리 항목

정책별로 정책 ID, 정책명, 운영 기관, 지원 지역, 지원 분야, 지원 내용, 연령과 소득 조건, 신청 시작일과 마감일, 신청 방법, 공식 출처 URL, 마지막 확인일, 데이터 출처를 관리한다. 가구와 부모님 관련 자격 조건, 공식 확인된 중복 수혜 제한 사항과 근거도 함께 관리한다.

부모님 소득과 재산의 실제 입력값은 서버에 영구 저장하지 않는 것을 원칙으로 한다. 기억하기를 켠 경우에만 사용자 브라우저에 30일 저장한다.

### 6.5 데이터 처리 과정

1. 공식 API에서 정책정보 수집
2. 원본 데이터 보관과 출처 기록
3. 서비스 내부 데이터 구조로 정규화
4. 중복 정책 확인과 통합
5. 정책 자격 조건의 구조화
6. 정책 검색용 저장과 색인(구조화 DB 조건 중심)
7. 검증된 정책정보를 서비스에 제공

수집과 검색은 가능한 범위에서 자동화하되, 조합에 쓰는 조건과 금액, 중복 제한은 사람이 검수한다.

### 6.6 데이터 최신성 관리

- 데이터별 마지막 확인일 기록
- 모집상태를 확인할 수 없으면 확인 필요 안내
- 신청기간이 지난 정책은 조합에서 빼고 따로 표시
- 공식 출처 내용과 차이가 발견되면 재검증
- API 오류 시 오래된 정보를 최신 정보로 표현하지 않음

### 6.7 개인정보 보호

- 회원가입 없이 핵심 기능 이용
- 주민등록번호 등 고유식별정보 수집 제외
- 서버와 로그에 사용자 조건 저장 금지 (요청 ID, 소요 시간, 오류 코드만 기록)
- 특수 조건(수급, 차상위, 한부모, 장애 등)과 부모님 소득, 재산은 LLM과 임베딩 API로 보내지 않음
- 외부 AI 서비스에는 민감하지 않은 조건만 전달
- 개인정보 처리와 AI 사용 사실 안내

### 6.8 데이터 관련 위험과 대응

- API 승인 지연: 공식 정책 페이지에서 확인한 데이터로 검색과 진단 기능을 개발한다.
- 정책별 자격 조건 형식 차이: 공통 비교 조건부터 구조화하고 복잡한 예외는 확인 필요로 표시한다.
- 정책정보 변경: 출처와 확인일을 기록하고 모집상태를 임의로 확정하지 않는다.
- 자동 판정의 잘못된 자격 판단: 명확한 조건은 코드로 비교하고, 설명은 판정 근거 템플릿으로 작성한다.

## 7. 정책 분석과 설명

### 7.1 데이터 분석·정제와 요청 처리

윤정찬이 수집한 원문·출처·버전·코드표를 탁서윤과 함께 분석·정제해 조건·금액·중복 제한·지급 시점·근거로 구조화한다. 검수한 데이터를 바탕으로 백엔드가 선택 조건을 비교한다. 문장 조건의 복잡함은 우선 데이터 품질·검수 과제로 처리하고 불확실한 부분은 확인 필요로 남긴다.

### 7.2 정책 검색과 근거 조회

MVP는 취업·주거 분류와 나이·지역 등 구조화된 필드로 후보를 조회하고 조건에 연결된 원문 인용을 가져온다. 기본 나이 상한이나 검색 순위만으로 복무 연장·예외 후보를 잘라내지 않는다. 검색 결과가 없음과 DB 오류를 구분한다.

### 7.3 분석 흐름과 설명

일반 application 코드가 검색·상세 조회·자격 판정·조합 계산·상황 변화·신청 안내를 요청에 맞게 실행한다. 실제 처리 단계는 SSE로 전송하며 오류 이후 성공 결과를 보내지 않는다. 추천 이유와 지금 할 일은 검수된 근거와 판정·계산 결과를 템플릿으로 정리한다. 근거가 없는 안내나 수급 자격 확정 문장을 만들지 않는다.

RAG·Agent·LLM·임베딩은 사용자 기능의 필수 조건이 아니다. 필요성이 확인되면 데이터 정제 보조나 문서 검색 등의 도입 목적과 효과를 별도로 평가한다. 현재 모델 선정 담당이나 AI 전담을 새로 지정하지 않는다.

### 7.4 자격 진단 로직

- 조건마다 충족, 미충족, 확인 필요로 판정한다.
- 모름과 건너뛴 값이 필요하면 확인 필요로 둔다. 미입력을 충족으로 처리하지 않는다.
- 코드로 판정할 수 없는 문장 조건은 확인 필요와 원문 인용으로 둔다.
- 나이 상한은 공고 근거가 있는 정책에만 실제 복무기간과 해당 정책의 연장 상한을 적용한다. 복무기간 구간 전체가 통과하거나 실패할 때만 확정하며, 구간 상한을 확정 개월로 올리지 않는다.
- 소득은 금액 구간을 기준 중위소득 비율로 바꿔 비교한다. 구간이 기준선에 걸치면 확인 필요로 둔다.
- 기혼이면 부모님 입력 단계를 생략한다. 부모 기준 면제는 정책별 근거로 확인하며, 필요한 정보가 없으면 확인 필요로 남긴다.
- AI는 코드 판정 결과를 임의로 변경하지 않고 판단 근거를 이해하기 쉽게 설명한다.

### 7.5 조합 계산 원칙

- 대상은 미충족이 없고 검수 완료이며 지금 신청할 수 있는 정책이다.
- 공식 근거로 함께 받을 수 없는 쌍은 같은 조합에 넣지 않는다.
- 근거가 없는 쌍은 넣고 확인 필요로 표시한다.
- 금액을 모르는 정책도 노출하지만 0원으로 취급하지 않는다. 확인된 금액의 합과 미상 항목을 구분하고, 미확인 금액까지 포함한 전체 최댓값을 확정했다고 안내하지 않는다.
- 기간 1년, 2년, 전체 금액을 구하고, 현재가치를 켜면 할인 금액으로 순위를 다시 매긴다.
- 할인율은 한국은행 기준금리를 매일 갱신해 쓰고 화면에 표시한다.
- 전체 후보에서 안전한 탐색으로 최적 조합을 구한다. 금액 상위 20개만 잘라 최적이라고 표시하지 않고, 계산 한도를 넘으면 명시적인 실패를 반환한다. 금리·지급 시점이 미확인이면 현재가치를 추정하지 않는다.

### 7.6 AI 안전장치

1. 공식 출처가 확인된 정책만 추천한다.
2. 정책에 없는 자격 조건을 생성하지 않는다.
3. 사용자가 제공하지 않은 조건은 추정하지 않는다.
4. AI가 코드 판정 결과를 임의로 변경하지 않는다.
5. 정보가 충돌하거나 부족하면 추가 확인을 안내한다.
6. 정책별 출처 URL과 마지막 확인일을 표시한다.
7. 실제 생성형 AI 설명을 도입한 경우에만 해당 문장에 AI 표시를 한다.
8. 최종 수급 자격은 해당 기관에서 확인하도록 안내한다.

## 8. 시스템 구성 계획

본 서비스는 React SPA와 FastAPI 모듈형 모놀리스, PostgreSQL을 중심으로 개발한다. 분석 흐름과 수집은 같은 Python 백엔드의 모듈이며 별도 AI 서비스 배포를 전제하지 않는다. RAG/Agent/LLM/임베딩은 필수 아님, 후속 필요성 검증 전 기술 미정이다.

### 8.1 전체 시스템 구조

1. Frontend: 13단계 조건 입력, 로딩과 진행 표시, 조합 비교, 자격 진단 카드, 정책 상세, 상황 변화 화면, 기억하기와 이미지 저장
2. Backend: 사용자 요청 처리, 정책 검색과 추천 API, 분석 흐름 실행, 자격 진단 로직, 조합 계산, 신청 안내
3. 백엔드 내부 분석 흐름 모듈: 순서대로 실행하는 일반 application 코드, 판정 근거 템플릿으로 추천 이유와 신청 안내 생성
4. Database: 정책 기본정보, 정책별 자격 조건, 공식 출처와 확인일, 정책 검색용 문서, 검수 상태와 중복 제한 근거
5. 외부 데이터: 온통청년 청년정책 API, 공공서비스와 보조금24 API, 한국은행 기준금리

2026-10-27에 React와 TypeScript, Vite, Python과 FastAPI, PostgreSQL 조합을 확정했다. 상세 결정은 [ARCHITECTURE.md](ARCHITECTURE.md) 9장을 기준으로 한다.

### 8.3 주요 API와 데이터 형식

API와 데이터 형식의 상세는 [REQUIREMENTS_v2.md](../REQUIREMENTS_v2.md) 6장을 기준으로 하되, 필드 이름과 자료형, 11.2의 임시 기본값은 다음 회의 확정 대상이다. RAG/Agent/LLM/임베딩은 필수 아님, 후속 필요성 검증 전 기술 미정이다. 현재 정렬 상태는 개발 초안 기준이며 기획자 최종 승인으로 쓰지 않는다.

- 메타와 선택지 조회, 분석 시작(SSE), 상황 변화 계산, 정책 상세 조회
- 분석 진행 상황은 서버가 전송하는 진행 이벤트로 화면에 표시한다.
- 하루 사용 상한은 서버 전체 100회이며, 자정에 초기화한다.

### 8.4 보안과 안정성

- 외부 AI와 정책 API 키는 환경변수로 관리한다.
- 인증키와 개인정보를 GitHub에 올리지 않는다.
- 외부 API 오류 시 오류 안내를 제공한다.
- 정책 검색 실패 시 존재하지 않는 정보를 생성하지 않는다.
- 정책 데이터가 오래된 경우 확인일을 표시한다.

### 9.3 GitHub 협업 방식

- GitHub 저장소를 공통 작업 공간으로 사용한다.
- 작업은 GitHub Issue로 등록하고 담당자를 지정한다.
- 각 팀원은 별도 브랜치에서 작업한다.
- 기능 구현 후 Pull Request를 생성한다.
- 다른 팀원이 변경사항을 검토한 후 병합한다.
- main 브랜치는 배포 가능한 상태를 유지한다.
- 주요 결정과 변경사항을 문서에 기록한다.

허용 브랜치 접두어는 feat, fix, docs, refactor, test, chore, ci다. main에서의 직접 작업을 금지한다. PR 전에는 작업 브랜치에서 최신 origin main을 머지하고, 충돌 해결과 검증을 마친다. 상태별 명령과 완료 기준은 [GIT_WORKFLOW.md](GIT_WORKFLOW.md)를 따른다.
