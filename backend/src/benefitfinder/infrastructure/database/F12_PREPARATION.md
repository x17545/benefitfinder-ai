# API 본문에서 F12 입력 자동 준비

수집 성공본의 PostgreSQL 레코드를 확인된 정책 매핑에 연결해 F12 대기 작업을 만든다. 매일 원문 JSON을 다시 작성하지 않고 바뀐 API 본문을 분석으로 넘긴다. 이 단계는 정책 사실 검수·승인·게시를 수행하지 않는다. [공식 API 안내](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiDoc)와 해당 환경의 실제 응답으로 필드 의미·출처·정책 범위를 확인해야 한다.

## 매핑 준비

담당자가 Git 제외 JSON에 정책 ID·공식 이름/확인된 별칭·청년 취업/주거 분류, 수집 레코드 ID, 이름/본문 필드·분류 확인값을 기록한다. 금액·자격 검수 전에 분석 대상의 출처와 범위를 확인하는 설정이다. 제목으로 분야를 추정하거나 목록 전체를 MVP에 포함하지 않는다.

다음은 **가상 예제**이며 `support`, `category`, `ageScope`는 설명용 가상 필드다. 실제 필드와 값을 확인해 바꿔야 한다.

```json
{
  "format_version": 1,
  "policies": [{
    "id": "youth:fictional:A",
    "name": "가상 청년 취업 A",
    "categories": ["employment"],
    "aliases": []
  }],
  "targets": [{
    "policy_id": "youth:fictional:A",
    "documents": [{
      "external_id": "A",
      "name_field": "plcyNm",
      "body_fields": ["support", "timing"],
      "scope_guards": {
        "category": "fictional-employment",
        "ageScope": "fictional-youth"
      }
    }]
  }]
}
```

- `policies`와 `targets`는 각각 1~100개, 대상마다 문서는 1~4개다. 대상은 정책 목록에 있어야 하며 중복 정책·원천·본문 필드를 거부한다.
- `name_field`는 정책 이름 또는 확인된 별칭과 정확히 같아야 한다. `scope_guards`의 1~8개 필드/문자열도 정확히 비교한다. 이름·분류가 바뀌면 매핑을 다시 확인한다.
- `body_fields`는 1~40개다. 지정한 문자열·정수를 `[필드 이름]` 다음 줄에 그대로 옮긴다. HTML도 실행·탐색 없이 원형으로 보존한다. 빠진 값은 생략하며 본문이 모두 없으면 실패한다. 금액 단위·지급일·미확인 값을 추가하지 않는다.
- 키·담당자 이름·연락처·프로필·부모 정보·조회수로 식별되는 필드를 거부한다. 지정하지 않은 원천 필드는 모델 입력에 포함하지 않는다. 사용자 조건은 받지 않는다.
- 설정은 256KiB 이하이며 중복 JSON 키·NaN·알 수 없는 필드·승인 필드를 거부한다. F12의 문서당 10만 자·합계 20만 자·입력 2MiB 한도를 유지하며 초과 자료를 잘라 등록하지 않는다.

## 실행과 일일 연결

기존 0001·0002·0005·0006·0007이 필요하며 새 마이그레이션·의존성은 없다. [F12 작업 역할](F12_ANALYSIS.md#db와-실행)의 수집 세 테이블 SELECT와 큐 쓰기 권한을 사용한다. 준비 조회는 읽기 전용이며 모델·원격 HTTP·API 키가 필요하지 않다.

```sh
uv run --locked python -m benefitfinder.jobs f12-analysis prepare \
  --plan data/local/f12-preparation.json
```

`F12_WRITE_DATABASE_URL`로 연결해 `targets`, `registered`, `replayed`, `failed` 네 건수만 출력한다. 전부 등록/재사용하면 0, 일부 실패는 1, 설정·DB·파일 오류는 고정 오류와 2다. 독립 대상의 성공을 유지하며 건수는 사람 검수 완료를 뜻하지 않는다.

매일 실행에는 `F12_PREPARATION_PLAN`에 매핑 파일 경로를 설정한다. `refresh-data`는 정책·ECOS 수집 뒤 **입력 준비 → F12 큐 분석 → 단일 Discord 보고** 순서로 실행한다. 수집·준비가 일부 실패해도 다음 단계의 독립 작업은 시도하고 전체 실행은 실패로 기록한다. 이전 전체 성공 기록은 유지한다. 미설정이면 기존 흐름이며, 설정했는데 F12 DB가 없으면 준비 실패다.

## 동일 자료·변경·오류

원천 해시는 수집기의 정책 내용 해시와 다시 비교한다. 문서 버전 `api-v1:<해시>`는 원천 해시와 정확한 본문 표현을 함께 묶는다. `collected_at`은 해당 내용을 완전한 수집 생성본으로 받아들인 이벤트 시각이다. 같은 내용의 재수집은 이를 갱신하지 않아 입력 재등록이 LLM을 다시 호출하지 않는다. 공식 게시일이나 사람 검수일이 아니다.

원천 변경은 이전 F12 작업을 `stale`로 만들고 다음 준비에서 새 버전을 등록한다. 누락 원천은 등록하지 않는다. 재등장도 예전 작업을 복구하지 않고 새 이벤트의 입력을 준비한다. 준비 중 원천이 바뀌면 등록 트랜잭션이 현재 해시·시각을 재검사한다. 본문 준비·LLM 호출 중 원천 잠금을 잡지 않는다.

정책명/분류 불일치·본문 없음·잘못된 유형·한도 초과·원천 불일치는 대상 실패다. 콘솔·통합 상태·Discord에는 원문·정책명·URL·자격 증명·외부 예외를 넣지 않는다. Agent 입력·실행 기록은 기존 권한 700/600 로컬 산출물과 검수 대기 상태로 인계한다.

이 단계는 저장된 **공식 API 본문**의 자동 준비다. API에 없는 첨부 공고·지침·FAQ 확보/변경 추적, 보조금24, 실제 대상 매핑·사람 검수·운영 스케줄·알림 도착은 남아 있다. API 본문만으로 조건·금액·예외가 충분하다고 판단하지 않는다. 추가 문서는 기존 [명시적 문서 입력 등록](F12_ANALYSIS.md#입력-준비)과 검수 절차를 따른다.

개발 통합 검증에서는 가상 API 생성본→PostgreSQL 준비→이 PC의 llama.cpp/CUDA→검수 자료까지 실행했다. 4종 도구 9회 호출로 명시된 20만 원을 보존하고 검수 대기로 남겼다. 같은 내용의 두 번째 실행은 입력을 재사용하고 모델을 호출하지 않았으며 계산용 카탈로그는 0행이었다. 실제 API·정책 사실 검수·운영 스케줄 검증은 별도다.
