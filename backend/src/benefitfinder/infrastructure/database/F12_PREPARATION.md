# API·공식 보충 문서에서 F12 입력 자동 준비

수집 성공본의 PostgreSQL 레코드를 확인된 정책 매핑에 연결해 F12 대기 작업을 만든다. 매일 원문 JSON을 다시 작성하지 않고 바뀐 API 본문과 명시한 [공식 HTML·PDF](OFFICIAL_DOCUMENTS.md)를 함께 분석으로 넘긴다. 이 단계는 정책 사실 검수·승인·게시를 수행하지 않는다. [공식 API 안내](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiDoc)와 해당 환경의 실제 응답으로 필드 의미·출처·정책 범위를 확인해야 한다.

## 매핑 준비

담당자가 Git 제외 JSON에 정책 ID·공식 이름/확인된 별칭·청년 취업/주거 분류, 수집 레코드 ID, 이름/본문 필드·분류 확인값을 기록한다. 금액·자격 검수 전에 분석 대상의 출처와 범위를 확인하는 설정이다. 제목으로 분야를 추정하거나 목록 전체를 MVP에 포함하지 않는다.

다음은 **가상 예제**이며 `support`, `category`, `ageScope`는 설명용 가상 필드다. 실제 필드와 값을 확인해 바꿔야 한다.

```json
{
  "format_version": 1,
  "scope": {
    "category_field": "category",
    "category_values": {
      "employment": ["fictional-employment"],
      "housing": ["fictional-housing"]
    }
  },
  "policies": [{
    "id": "youth:fictional:A",
    "name": "가상 청년 취업 A",
    "categories": ["employment"],
    "aliases": []
  }],
  "targets": [{
    "policy_id": "youth:fictional:A",
    "documents": [{
      "external_id": "A",
      "name_field": "plcyNm",
      "body_fields": ["support", "timing"],
      "scope_guards": {
        "category": "fictional-employment",
        "ageScope": "fictional-youth"
      }
    }]
  }]
}
```

- `policies`와 `targets`는 각각 1~100개, 대상마다 문서는 1~4개다. 대상은 정책 목록에 있어야 하며 중복 정책·원천·본문 필드를 거부한다.
- `scope`에는 공식 응답에서 확인한 분류 필드와 취업/주거의 정확한 값 목록을 각각 1~50개 지정한다. 현재 원천 값으로 판별한 문서들의 분류 합집합이 정책의 `categories`와 같아야 한다. 미확인·범위 밖·다른 분류는 등록하지 않는다. 복합 분류 문자열도 분리해 추정하지 않고 확인한 전체 값을 매핑한다.
- `name_field`는 정책 이름 또는 확인된 별칭과 정확히 같아야 한다. `scope_guards`의 1~8개 필드/문자열도 정확히 비교한다. 이름·분류가 바뀌면 매핑을 다시 확인한다.
- `body_fields`는 1~40개다. 지정한 문자열·정수를 `[필드 이름]` 다음 줄에 그대로 옮긴다. HTML도 실행·탐색 없이 원형으로 보존한다. 빠진 값은 생략하며 본문이 모두 없으면 실패한다. 금액 단위·지급일·미확인 값을 추가하지 않는다.
- 키·담당자 이름·연락처·프로필·부모 정보·조회수로 식별되는 필드를 거부한다. 지정하지 않은 원천 필드는 모델 입력에 포함하지 않는다. 사용자 조건은 받지 않는다.
- 설정은 256KiB 이하이며 중복 JSON 키·NaN·알 수 없는 필드·승인 필드를 거부한다. F12의 문서당 10만 자·합계 20만 자·입력 2MiB 한도를 유지하며 초과 자료를 잘라 등록하지 않는다.

## 수집한 공식 보충 문서 연결

대상의 선택 필드 `official_documents`에 수집 계획의 안정된 `external_id`와 F12에서 사용할 `document_id`를 명시한다. 예를 들어 위 `targets[0]`에 다음을 추가한다. 모든 값은 가상이다.

```json
"official_documents": [{
  "external_id": "fictional-notice",
  "document_id": "official:fictional-notice"
}]
```

API 문서와 합해 최대 4개다. 수집 DB의 `official_documents`에서 미누락·현재 해시·같은 정책·취업/주거 분류·추출 성공·텍스트 해시를 검증하고 보존한 정규화 본문을 그대로 사용한다. 확인되지 않은 링크·원문을 추가로 탐색하지 않는다. 기존에 수동 등록한 같은 공고를 갱신하려면 **그 문서의 기존 ID를 `document_id`에 명시**한다. 이름·URL 유사성으로 문서를 삭제·대체하지 않는다. 계획에 없는 기존 문서는 계속 보존하며 한도를 넘으면 실패한다.

보충 문서가 있는 대상은 각 입력 문서의 원천을 `document_sources`로 명시하고 모든 원천의 현재 내용 해시를 `collection_sources`에 고정한다. 문서 버전은 `official-v1:<원천 내용 해시>`이며 시각은 그 원천의 현재 내용 수락 이벤트다. 서로 다른 문서가 같은 시각에 수집됐다고 꾸미지 않는다. DB 등록은 원천·정책 잠금 아래에서 각 연결 문서의 자체 변경 시각을 확인하며, 공식 보충 문서는 저장 본문·URL·버전과도 정확히 비교한다. 바뀌지 않은 API/보충 문서는 원래 시각을 유지하면서 다른 원천의 변경과 함께 새 분석 입력을 구성할 수 있다.

추출 실패·삭제·다른 정책·본문/해시 불일치는 해당 대상의 준비 실패다. 해당 보충 문서를 빼고 API만 등록하거나 기존 초안을 되살리지 않는다. API 전용 기존 계획에는 `document_sources`를 추가하지 않아 기존 입력 해시와 재사용 동작을 유지한다.

## 실행과 일일 연결

기존 0001·0002·0005·0006·0007과 분석 버전 전환의 0011이 필요하다. 보충 문서 연결은 원천 확장의 0012가 필요하다. 준비 자체의 별도 의존성은 없다. [F12 작업 역할](F12_ANALYSIS.md#db와-실행)의 수집 세 테이블 SELECT와 큐 쓰기 권한을 사용한다. 준비 조회는 읽기 전용이며 모델·원격 HTTP·API 키가 필요하지 않다.

```sh
uv run --locked python -m benefitfinder.jobs f12-analysis prepare \
  --plan data/local/f12-preparation.json
```

`F12_WRITE_DATABASE_URL`로 연결해 `targets`, `registered`, `replayed`, `failed` 네 건수만 출력한다. 전부 등록/재사용하면 0, 일부 실패는 1, 설정·DB·파일 오류는 고정 오류와 2다. 독립 대상의 성공을 유지하며 건수는 사람 검수 완료를 뜻하지 않는다.

매일 실행에는 `F12_PREPARATION_PLAN`에 매핑 파일 경로를 설정한다. `refresh-data`는 정책·ECOS 수집 뒤 **입력 준비 → F12 큐 분석 → 단일 Discord 보고** 순서로 실행한다. 수집·준비가 일부 실패해도 다음 단계의 독립 작업은 시도하고 전체 실행은 실패로 기록한다. 이전 전체 성공 기록은 유지한다. 미설정이면 기존 흐름이며, 설정했는데 F12 DB가 없으면 준비 실패다.

## 동일 자료·변경·오류

원천 해시는 수집기의 정책 내용 해시와 다시 비교한다. 문서 버전 `api-v1:<해시>`는 원천 해시와 정확한 본문 표현을 함께 묶는다. `collected_at`은 해당 내용을 완전한 수집 생성본으로 받아들인 이벤트 시각이다. 같은 내용의 재수집은 이를 갱신하지 않아 같은 분석 버전의 입력 재등록이 LLM을 다시 호출하지 않는다. 분석 의미 변경에 따른 버전 전환은 [분석 큐](F12_ANALYSIS.md)의 정상 재분석 절차를 따른다. 공식 게시일이나 사람 검수일이 아니다.

자동 준비는 마지막으로 등록한 입력의 공식 보충 문서를 유지한다. API만 들어 있는 계획을 실행해도 명시적으로 추가한 공고·PDF·FAQ를 빼거나 기존 검수 초안을 API만의 새 초안으로 대체하지 않는다. 문서 순서와 동일 API 본문의 확인 시각도 보존하며, 입력·분석 버전이 같으면 완료 작업을 재사용한다. 최신 원천의 수락 시각이 더 늦으면 새 시각을 사용한다. 병합과 등록은 원천·정책 잠금 안에서 실행하므로 동시 등록에도 같은 입력은 한 작업으로 연결된다.

원천 변경은 이전 F12 작업을 `stale`로 만든다. API와 계획에 명시한 보충 문서는 다음 준비에서 각자의 현재 내용으로 새 입력을 구성한다. 원천 연결이 없는 기존 수동 문서는 계속 전체 원천 중 가장 늦은 변경·재등장 이후에 확인돼야 한다. 이를 새로 수집한 것처럼 바꾸지 않으며 필요한 재확인이 없으면 해당 대상은 준비 실패로 남긴다. 담당자가 공식 문서를 다시 확보하고 전체 입력을 명시적으로 `f12-analysis register --input ...`에 등록하거나 수집 원천·기존 문서 ID를 계획에 연결해야 한다. 누락 원천은 등록하지 않는다. 재등장도 예전 작업을 복구하지 않는다. 준비 중 원천이 바뀌면 등록 트랜잭션이 현재 해시·시각·연결 본문을 재검사한다. 본문 준비·LLM 호출 중 원천 잠금을 잡지 않는다.

기존 입력의 원천 의존성을 자동 계획이 빠뜨렸거나 보충 문서를 합쳐 입력 한도를 넘으면 `f12_preparation_requires_full_input`으로 거부하고 기존 작업을 보존한다. 문서를 임의로 자르거나 원천 연결을 제거하지 않는다. 문서 삭제·대체나 복수 원천 변경은 전체 입력을 확인한 뒤 명시적 등록을 사용한다. 이 보존 기능이 공식 링크의 변경 감시를 대신하지는 않는다.

정책명/분류 불일치·본문 없음·잘못된 유형·한도 초과·원천 불일치는 대상 실패다. 콘솔·통합 상태·Discord에는 원문·정책명·URL·자격 증명·외부 예외를 넣지 않는다. Agent 입력·실행 기록은 기존 권한 700/600 로컬 산출물과 검수 대기 상태로 인계한다.

이 단계는 저장된 공식 API와 명시적으로 연결한 보충 문서의 자동 준비다. 실제 대상 확대·범위 확인·사람 검수·운영 스케줄·알림 도착은 남아 있다. API나 연결 문서만으로 조건·금액·예외가 충분하다고 판단하지 않는다. 추가 문서와 원문 간 상충은 기존 [명시적 문서 입력 등록](F12_ANALYSIS.md#입력-준비)과 검수 절차를 따른다.

개발 통합 검증에서는 가상 API 생성본→PostgreSQL 준비→이 PC의 llama.cpp/CUDA→검수 자료까지 실행했다. 4종 도구 9회 호출로 명시된 20만 원을 보존하고 검수 대기로 남겼다. 같은 내용의 두 번째 실행은 입력을 재사용하고 모델을 호출하지 않았으며 계산용 카탈로그는 0행이었다. 실제 API·정책 사실 검수·운영 스케줄 검증은 별도다.


`source: gov24` 계획과 `GOV24_PREPARATION_PLAN`의 별칭 필드·연령 검사·실행/검수 경계는 [보조금24 안내](GOV24.md)를 따른다. 미지정 `source`는 기존 온통청년이다. 같은 정책을 두 자동 계획에 배정하면 중복 준비를 거부하며 복수 원천을 한 입력에 명시적으로 등록한다.
