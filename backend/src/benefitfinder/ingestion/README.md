# 데이터 수집·정제

작업 전에는 루트 지침과 이 경로의 [추가 에이전트 지침](AGENTS.md)을 함께 읽는다.

현재 구현: 온통청년 정책 목록의 원천 수집·원본 보관·버전 비교(`youthcenter.py`, `versioning.py`, `collect.py`)와 규칙 후보의 근거 검사·명시적 검수 기록(`policy_rule_review.py`). 네트워크·원본 저장·버전 저장은 `application/collection.py`의 인터페이스로 주입받는다. 공용 DB가 정해지기 전까지는 infrastructure의 HTTP 어댑터와 로컬 JSON 파일 저장소로 실행한다. 공고 원문 수집·실제 Agent·혜택 정규화·검수 저장/게시·PostgreSQL 저장과 매일 실행·알림은 아직 연결하지 않았다.

- `collect_youthcenter()`는 모든 응답을 해석 없이 스냅숏(요청 파라미터·수집 시각·상태·SHA-256)으로 보관하고 정책 ID별 레코드 해시로 신규·변경·유지·삭제를 구분한다.
- API 키는 요청 파라미터·스냅숏·오류에 넣지 않는다. 어댑터가 직접 추가하고, 어댑터 예외는 형식 이름만 기록한다.
- 페이지·레코드 오류(응답 상태, 형식, ID 누락, 같은 ID의 다른 내용, 페이지 상한)는 성공 데이터와 분리한다. 하나라도 실패하면 `complete=False`이며 삭제 감지를 하지 않는다.
- 2026-10-30 실제 응답 표본으로 확인한 설정은 `YOUTHCENTER_POLICY_LIST`다. 정책 ID는 `plcyNo`, 목록은 `result.youthPolicyList`, 전체 건수는 `result.pagging.totCount`이고 `resultCode`가 200이 아니면 실패로 처리한다. 테스트는 같은 필드 이름에 가상 값을 넣는다.
- 조회수(`inqCnt`)는 정책 내용과 무관하게 바뀌므로 변경 판정 해시에서 뺀다. 담당자 이름(`sprvsnInstPicNm`, `operInstPicNm`)은 수집 레코드에 저장하지 않는다. 원본 스냅숏에는 응답 전체가 남으므로 원본 보관 위치·기간은 개인정보 기준으로 별도 정한다.
- 한 페이지 최대 건수는 아직 확인하지 않았다. 마지막 페이지까지 예상 건수를 확인하며 부족하면 `short_page`·`unexpected_empty_page` 오류로 멈춘다. 수집 중 전체 건수가 바뀌거나 최종 고유 ID 수가 전체 건수와 다르면 정상 완료·삭제 감지를 허용하지 않는다.
- 저장소에는 레코드와 별도로 시간대가 있는 실행 확인 시각(`checked_at`)을 전달한다. 정상 응답이 0건이어도 기존 정책의 삭제 감지 시각을 기록하고 활성 목록에서 제외한다.

원천 API 응답의 파싱·정규화·중복 처리·품질 검증과 게시 흐름을 둔다. API만으로 확인되지 않는 중복 제한·예외는 공식 공고·지침·FAQ를 보완 수집하고 Agent 추출 인터페이스로 연결한다. 조건·방향·기간·예외·금액 영향·근거 버전을 보존한 후보를 검증·사람 검수 후 게시한다. 상세는 [정책 데이터 분석·정제](../../../../docs/architecture/POLICY_DATA_PIPELINE.md)를 따른다.

네트워크·저장 어댑터는 주입받고 실행 주기는 jobs가 담당한다. API 필드 누락을 동시 수급 허용으로 해석하지 않으며, 미지원·상충·불명확은 검수 대기로 남긴다. 실제 원본·정제 결과는 Git 제외 경로에서 다룬다.

윤정찬은 API·공식 원문 수집·원본/출처/버전 관리와 PostgreSQL 적재를, 탁서윤은 데이터 정제·조건 구조화·품질 검증과 ai 원문 분석·중복 수혜 규칙 추출·자동화를 맡는다. 서윤의 정제·검수 결과를 정찬이 원본·검수 대기·게시 상태와 구분해 적재하고, 양승현이 게시된 조건·금액·중복 제한·근거를 API·판정·조합 계산에 연결한다. 수집·적재 실행 함수와 실패·재검수 결과는 서윤의 jobs 자동화로 연결한다. 구체 DB 쓰기는 infrastructure 어댑터에 두며, 작업은 Issue에서 파일별로 나눈다.

## 규칙 후보의 근거 검사와 검수

`application/policy_rules.py`는 데이터 준비 내부의 문서·후보·검수 기록과 `RuleExtractor` 인터페이스다. 게시 혜택 JSON 계약이나 확정 DB 스키마가 아니며, 현재 온라인 계산에 연결하지 않는다. `policy_rule_review.py`는 아래 순서로 호출한다.

1. 수집 담당이 확인한 공식 원문을 `SourceDocument`로 전달한다. 문서 ID·정책 ID·HTTPS 출처·버전·시간대가 있는 수집 시각·텍스트를 보존한다. `official`은 기본 `False`이며, URL 모양만으로 공신력을 판정하지 않는다. 호출자가 출처를 확인한 문서만 `True`로 설정한다. PDF/HTML 텍스트 추출과 원본 스냅숏 연결은 후속 수집 어댑터가 맡는다.
2. `prepare_rule_reviews(documents, policies, extractor)`가 공식 문서만 주입된 추출기로 보내고, 후보의 정책 연결·원문 인용·SHA-256·버전·근거 위치를 검사한다. 모든 적용 정책은 청년 취업·주거 범위여야 한다. 빈 추출 결과는 제한이 없다는 뜻이 아니며, 어떤 후보도 자동 승인하지 않는다.
3. 중복 후보 ID나 같은 정책 쌍의 여러 후보는 배치 검수 문제로 남긴다. 조건·예외·방향·기간·금액 영향·미해결 별칭은 원형을 보존한다. 현재 승인 대상은 근거가 일치하는 무조건 양방향 동시 수급 금지뿐이며, 나머지는 코드 지원·계약 검토까지 대기한다. 인용 일치는 의미·누락 검증을 대신하지 않으므로 검수자가 전체 공고·예외·상충을 읽어 확인해야 한다.
4. 사람이 원문을 검토한 뒤 `approve_candidate(review, documents, policies, candidates=..., reviewer=..., reviewed_at=...)`를 명시적으로 호출한다. 검사 문제가 있는 기록은 승인할 수 없다. 검수자·검수 시각과 후보·전체 입력 문서 세트의 해시를 연결하며, 이 호출은 게시나 금액·지급 시점 검수를 뜻하지 않는다.
5. 사용 전 `refresh_review(review, documents, policies, candidates=...)`를 호출한다. 후보 내용, 문서 텍스트·버전·출처·연결 정책, 문서 세트나 지원 범위가 바뀌면 승인을 해제한다. 승인 후 같은 쌍의 다른 후보가 추가돼도 해제한다. 같은 원문을 다시 수집해도 기존 검수 시각을 갱신하지 않는다. 이때 기존 검수 시각이 새 수집 시각보다 앞서는 것은 허용한다. 기존의 모든 검수 대기 사유는 반복 갱신해도 보존한다. 사유를 해소하려면 전체 배치를 새로 준비하고 사람이 다시 검토해야 한다. 승인 기록이 있더라도 미해결 사유가 추가된 기록의 상태는 `needs_review`다.

승인·갱신에는 인용된 문서만이 아닌 당시 배치의 전체 문서 세트, 현재 유효한 정책 목록, 검토할 전체 후보 튜플(`candidates`)을 전달해야 한다. 후보 일부만 넘기는 호출은 전체 배치의 무상충을 보장하지 못한다. 실제 저장 연동에서는 이 세트를 일관되게 조회하고 기존 게시 규칙과의 상충도 함께 검사해야 한다.

검사·추출 실패는 고정 오류 코드로 반환하고 외부 예외 원문을 노출하지 않는다. 이 모듈은 저장소를 쓰지 않으므로 마지막 성공 자료 보존·재검수 적재·게시 버전 전환은 후속 저장 연동에서 보장해야 한다. 실제 LLM 없이 가짜 추출기를 사용한 회귀 검증:

```bash
uv run --locked python -m unittest backend.tests.test_policy_rule_review -v
```

## 로컬 수집 실행

```bash
uv run --locked python -m benefitfinder.jobs collect-youthcenter
```

인증키는 환경 변수 `YOUTHCENTER_API_KEY`로만 전달한다. 저장소 루트에서 실행하면 아래 Git 제외 경로에 결과가 생긴다.

| 경로 | 내용 |
|---|---|
| `data/raw/youthcenter/snapshots/` | 페이지별 원본 응답과 `.meta.json`(요청 파라미터·수집 시각·상태·해시, 키 제외) |
| `data/processed/youthcenter/records.json` | 정책 ID별 최신 레코드(담당자 이름 제외), 마지막 확인 시각, 삭제 감지 시각 |
| `data/processed/youthcenter/changes.jsonl` | 신규·변경·삭제 이력 |
| `data/processed/youthcenter/pending.json` | 저장 중단 시 복구에 쓰는 임시 기록. 정상 저장·복구 후 삭제 |
| `data/processed/youthcenter/records.csv` | 최신 레코드 CSV(엑셀용 UTF-8 BOM) |
| `data/processed/youthcenter/fields.csv` | 필드별 채워진 건수·서로 다른 값 수·예시. 구조 공유용 |

전체 수집에 성공하면 종료 코드 0, 일부 실패하면 성공분만 저장하고 1을 돌려준다. 요청 사이에는 0.5초 간격을 둔다. 공식 서버가 가끔 일시적인 500을 돌려주므로(2026-10-30 실행에서 확인), 같은 요청이 5xx·연결 오류면 2·4·8초 간격으로 최대 3번 다시 시도한다. 그래도 실패하면 그 페이지에서 멈추고, 다시 실행하면 받은 레코드는 `unchanged`로 이어진다. 실제 데이터 파일은 PR에 첨부하지 않고 공유 방법은 팀에서 정한다.

로컬 저장은 복구 기록을 먼저 남긴 뒤 변경 이력과 최신 레코드를 반영한다. 파일 쓰기·교체에 실패하면 예외로 종료하며, 다음 저장소 읽기나 재실행 때 미완료 저장을 먼저 복구한다. 부분 기록·재실행으로 변경 이력이 빠지거나 중복되지 않도록 기존 이력의 끝 위치부터 복구한다. 같은 `--data-dir`에는 한 번에 한 수집 프로세스만 실행한다.
