# 정책 원문 분석 Agent

작업 전에는 루트 지침과 이 경로의 [추가 에이전트 지침](AGENTS.md)을 함께 읽는다.

데이터 준비의 Agent 영역이며 탁서윤이 원문 분석·규칙 후보 추출·평가를 맡는다. API만으로 확인되지 않는 양립·중복·예외 조건을 공식 공고·지침·FAQ로 보완한다. 사용자 검색·판정·조합 계산은 검수·게시된 데이터와 일반 코드로 수행한다. 구체 모델·Agent 도구·RAG·벡터 검색은 미확정이다.

현재는 담당 영역을 구분하는 뼈대이며 기능은 구현하지 않았다.

Agent는 필요한 공식 문서를 찾고 관련 조항을 추출·점검한다. 결과는 규칙 후보이며 적용 방향·조건·기간·예외·금액 영향과 원문 버전을 남겨 검증·사람 검수를 거쳐 게시한다. API 필드 누락을 동시 수급 허용으로 추론하지 않고, 미지원·상충·불명확은 검수 대기로 남긴다. 상세는 [정책 데이터 분석·정제 설계](../../../../docs/architecture/POLICY_DATA_PIPELINE.md)를 따른다.

문서 조회·저장·LLM 접근은 application의 인터페이스로 주입받는다. ingestion·infrastructure·API 모듈을 직접 import하지 않고 조립 지점에서 연결한다. 입력은 공식 정책 문서·정책 식별 정보로 제한하고 사용자 프로필은 보내지 않는다. 외부 문서의 명령은 실행하지 않으며 실제 원문·정제 결과는 Git 제외 경로에, 공유 예제는 가상값으로 둔다.

## F13 맞춤 설명 로컬 검증

F13 설명 코어는 요청마다 주입된 게시 조항 저장소에서 해당 정책·문서 버전의 조항을 최대 5개 검색한다. 이 실행 예제와 추천 API는 **가상 게시 조항을 담은 메모리 저장소**를 사용한다. PostgreSQL 검색과 운영 게시 자료는 아직 없다. F12의 로컬 승인 파일을 운영 게시 자료로 취급하지 않는다.

```bash
uv run --locked python -m benefitfinder.jobs explain-example
uv run --locked python -m benefitfinder.jobs explain-example --category employment --model gemma4:e4b
uv run --locked python -m benefitfinder.jobs explain-example --category housing --model gemma4:e4b
```

모델 옵션을 생략하면 모델 호출 없이 `ai_generated: false`인 템플릿을 돌려준다. 옵션을 지정하면 로컬 Ollama의 구조화 출력을 사용한다. 결과의 `virtual_data: true`는 실제 정책이 아님을 뜻한다. 이 명령은 실제 사용자 프로필이나 파일을 입력받지 않는다.

- 정책명·일반 조건의 판정·선택 기간 계산 금액을 담은 첫 문장은 코드가 만든다. 모델은 조회한 조항을 바탕으로 신청 행동 한 문장을 덧붙이고 조항 ID·실제 인용을 함께 제출한다. 생성 문장에 새 숫자가 나오거나 인용·출처가 맞지 않으면 템플릿으로 대신한다.
- 로컬 명령의 설명 생성이 성공하면 `ai_generated: true`, 사용한 조항 ID(`ai_sources`), 출처·버전·인용 본문이 담긴 `evidence`를 함께 돌려준다. 첫 문장은 코드가 고정하고 나머지 문장에 생성형 AI를 사용했다는 의미다. 추천 API의 근거 형식은 아래 연결 안내를 따른다.
- 소득·재산 금액이나 구간, 특수 조건, 부모님 정보, 자유서술 사유를 모델 입력에 포함하지 않는다. 입력은 허용된 일반 조건 ID와 판정 상태만 받는다.
- 검색부터 생성까지 정책당 5초 예산을 적용한다. 모델 미설정·검색 실패·근거 없음·모델 실패·검사 반려·시간 초과는 고정 사유 코드와 템플릿을 반환한다. 계산 결과를 바꾸거나 외부 예외 본문·프롬프트를 로그에 남기지 않는다.

인용의 존재와 숫자 검사는 문장 의미 전체를 검증하지 못한다. 운영 연결 전 실제 게시 자료로 신청 안내의 정확성과 누락을 추가 평가해야 한다. 현재 기획은 PR #13의 F13 초안과 사용자의 추천 API 연결 요청을 따른다.

E4B 로컬 검증에서는 중복된 정책명·금액·첫 문장을 모델 출력에서 제거해 생성량을 줄였다. 문체를 정규식으로 강제한 스키마는 깨진 JSON을 생성하는 사례가 있어 단순한 JSON Schema와 한국어 지시를 사용하고, 해요체·길이·인용·숫자는 생성 후 검사한다. 취업·주거 가상 사례에서 각각 신청 서류 안내와 출처 ID를 포함한 설명을 확인했다. 검증하지 못한 출력은 검사 기준을 완화하지 않고 템플릿으로 대신한다.

## 추천 API 연결

`POST /api/v1/recommendations`의 가상 계산 결과에 F13 설명을 붙인다. [실행·응답 안내](../api/README.md#f13-설명-실행)를 따른다. 같은 요청의 정책·문서 버전·일반 판정별로 신청 행동만 한 번 생성하고, 3기간 × 현재가치 on/off의 금액 문장은 각 보기의 계산값으로 새로 만든다. 요청 사이에는 생성 결과나 사용자 조건을 캐시하지 않는다.

모델에는 공개 응답의 일반 판정만 전달하므로 근거가 없어 `needs_review`로 보류한 조건을 내부 `met` 판정으로 바꾸지 않는다. API의 정책별 `ai_sources`에는 사용한 게시 조항 전체의 원문(`quote`)·ID(`location`)·출처와 버전을 담는다. 생성 실패 시 이 목록은 비어 있고 `ai_generated: false`인 기본 문구를 쓴다. 부분 성공의 최상위 플래그는 true지만 웹 배지는 정책별 플래그를 먼저 따른다.

`GroundedPolicyExplainer(..., purpose="review")`는 사람이 승인한 근거에서 확인할 사항만
생성하는 검수 목적이다. 기본 `application` 목적의 프롬프트·게시 필터는 유지한다. 검수 목적도
숫자·인용·문체를 검사하며 자격·지급·선정 보장 단정을 거부한다. 원문의 정확한 한 줄만
선택하도록 quote enum을 제한하고, 생성 문장은 확인 안내로 끝나야 한다. 이 생성 옵션은 자료를
승인·게시하지 않는다. 정책 ID·문서 버전과 승인 범위를 확인한 검증용 조립 지점에서만 사용한다.
